# KF-ADR-019f9388-a139-7355-b9f2-f6dd9aa91042: Docker-first Hub Starter is a product contract before it is an image

- Status: accepted; contract and static qualification staged
- Date: 2026-07-24
- Category: Agent Hub / installed product / container starter
- Contract: [`kungfu-hub-starter-docker.contract.json`](../../framework/hub-starter/kungfu-hub-starter-docker.contract.json)

## Context

Kungfu now has three distinct facts that are easy to over-compress into a false
product claim:

1. KFD publishes an experimental Agent Hub profile, Hub 20 vectors and verifier,
   plus four-language envelope-smoke scaffolds;
2. the clean-room `agent-hub-demo` proves that two independently implemented
   file-CAS Hubs can consume public KFD; and
3. one exact installed Kungfu macOS arm64 artifact passes Hub 20 through the
   product-owned `kungfu agent hub capabilities/handle` surface.

None of these facts provides a supported image, a safe one-command lifecycle,
volume and identity policy, restart or restore evidence, an upgrade contract,
or production operations. Shipping a Dockerfile first would freeze hidden
choices into an apparent product and let “container starts” masquerade as “Hub
is ready.”

## Decision

### 1. The first deliverable is a versioned product concept contract

Kungfu owns `kungfu.hub-starter-docker.concept/v1`. It fixes responsibility,
topology, safe defaults, identity, lifecycle, compatibility, upgrade, recovery,
observability, the evidence ladder, and non-claims. The contract is a welded
pre-release integration surface because later Compose, CLI, image, state and
operations work will bind to it.

This slice deliberately contains no Dockerfile, Compose bundle or implemented
starter CLI. It builds, publishes, pulls and runs no image and contacts no
Docker daemon. Only the static concept tier may be `passed`.

### 2. The default topology is one Hub plus an opt-in verifier

The persistent `hub` service owns one explicit `hub-home` volume and one writer
fence. The bounded `verify` job owns a separate evidence volume. Both are
non-root, read-only-root, unprivileged and Docker-socket-free. The default
network is private with no published ports; loopback exposure and egress are
explicit plan inputs.

Container/process identity is not Hub identity. Hub identity survives restart
in the authoritative volume and binds workspace, instance, contract, image
digest and volume generation. Semantic readiness, not process liveness, admits
the service.

### 3. “One command” means plan-bound lifecycle, not a hidden Compose alias

The future `kungfu hub starter up` command must render and validate a scoped
plan, bind immutable versions, validate ownership/network/fencing, and require
the exact plan root before apply. Unknown compatibility or uncertain state
blocks. Upgrade is side-by-side verify then commit; recovery restores to a new
empty volume and proves roots before readiness.

### 4. Protocol, demo, starter and production remain separate authorities

KFD owns protocol/scaffold/Hub 20. The clean-room demo is an adoption witness.
Kungfu Starter owns assembly and lifecycle UX. A production Hub implementation
owns semantic behavior, persistence, supported images and operations. No layer
may use evidence from another layer to claim its own unexecuted gate.

### 5. Promotion follows an explicit evidence ladder

Static contract, deterministic Compose render, daemon smoke, restart/fencing,
backup/restore, upgrade/rollback, and production admission are separate tiers.
Only the static contract tier passes in this change. Every future tier requires
retained, exact-source evidence and preserves all lower-tier non-claims.

## Consequences

- Product design becomes reviewable before an image or operational default can
  acquire accidental authority.
- The safe baseline is stricter than common Compose examples: no floating tags,
  host paths, public ports, host networking, privileged mode, Docker socket,
  root user, anonymous state, automatic migration or in-place restore.
- The future product must implement plan/apply receipts and semantic readiness;
  a thin wrapper around `docker compose up` is insufficient.
- Separate volumes and authority identities make restart, clone, backup,
  restore and rollback falsifiable rather than inferred from container state.
- The concept adds maintenance cost: contract/schema/checker/test/docs must move
  together under the source gate and KFD-1 register.

Rejected alternatives:

- **Publish an image now:** rejected because no Compose, daemon, restart,
  recovery, security or supported-platform evidence exists.
- **Promote `agent-hub-demo`:** rejected because it is an intentionally
  non-production clean-room witness, not Kungfu product authority.
- **Treat KFD scaffolds as the Hub:** rejected because they promise envelope
  smoke only and explicitly do not execute Hub 20.
- **One container with mutable host paths:** rejected because it conflates
  routing identity, state authority and operational convenience.

This decision is falsified if the checker permits a production/daemon tier to
pass, a floating image tag, multiple state writers, Docker socket or privileged
authority, real-Home mounting, public ports by default, missing non-claims, or
documentation that describes the concept as implemented.

# KF-ADR-019f86da-4f90-7b6b-ae6d-76cea57487f2: Buildchain promotion is the settlement boundary for ADR implementation truth

- Status: accepted
- Date: 2026-07-13
- Category: release governance / architecture evidence / Buildchain
- Related: [KF-ADR-019f86da-4f90-7739-aa31-52af27bc4470](KF-ADR-019f86da-4f90-7739-aa31-52af27bc4470.md) makes the
  adoption path the validation path; [KF-ADR-019f86da-4f90-7463-89b2-78cb94de9a0b](KF-ADR-019f86da-4f90-7463-89b2-78cb94de9a0b.md)
  binds welded surfaces to release versioning; the
  [document metadata contract](../development/document-metadata.md) separates
  decision, implementation, and review state.

## Context

ADR frontmatter is already the machine authority for implementation state, and
the documentation gate rejects malformed, unreachable, or contradictory
implementation evidence. That proves internal metadata consistency. It does not
prevent a feature from entering a channel without declaring which accepted
decision it advances, nor does it prove that a stable release has accounted for
every accepted decision.

Requiring every commit to name an ADR would use the wrong unit. Commits are
frequently rebased or squashed, ordinary fixes may have no architecture impact,
and a decision usually spans several coherent delivery stages. Kungfu already
has a stronger integration unit: protected pull requests flowing through
`dev -> alpha -> release`, with Buildchain owning the expensive qualification
boundary.

The missing mechanism is therefore not a commit-message convention. It is a
release-admissibility contract over pull-request intent, ADR projections, and
promotion evidence.

## Decision

Kungfu uses three increasingly strong ADR gates aligned with its existing
channel topology.

### Development: bounded delivery intent

A feature PR targeting `dev/*` must declare exactly one delivery intent:

- `stage-ready`: the PR completes a bounded, verified stage that is safe to
  integrate while the accepted ADR remains `partial` or `staged`;
- `implemented`: the accepted scope is an implementation-complete candidate,
  with qualification evidence present, awaiting promotion settlement.

This is a PR integration state, not an ADR lifecycle value. In particular,
`stage-ready` does not mean `implementation_status: staged`.

Non-feature fixes, tests, documentation, and chores retain an explicit
`adr-neutral` path. A feature branch cannot use that path, and an ADR-neutral PR
cannot modify an ADR record.

### Alpha: progress settlement after full qualification

An alpha promotion declares the ADR progress included in the promotion, or an
explicit reason that no ADR progress exists. Every declared projection must
match a changed accepted ADR record. The Buildchain candidate build runs the
same settlement gate after the full build and release qualification, so an
implementation-complete development claim becomes an implementation fact only
at an evidence-bearing promotion boundary.

### Stable: release admissibility

A stable promotion enumerates every ADR whose `decision_status` is `accepted`.
It admits the release only when each decision is:

- `implementation_status: implemented` with qualification evidence;
- `not-applicable`; or
- covered by an explicit waiver for the exact release and exact blocking
  conditions.

Proposed decisions are not obligations, and superseded decisions are historical
evidence rather than current obligations. Existing legacy metadata exemptions
do not count as stable waivers.

Stable waivers are versioned risk acceptances, not branch-protection bypasses.
They name the ADR, exact blocking conditions, reason, risk, mitigation, release
administrator, approval PR, and expiry release. The waiver ledger has a
dedicated CODEOWNER. A waiver must match the current stable PR and expires after
that exact version; it cannot silently carry forward.

## Machine authority

The contract is `docs/adr-release.contract.json`. Pull requests carry one JSON
manifest inside the `kungfu-adr-release:v1` marker. The validator emits a
`kungfu.adr-release-report/v1` report containing admitted, waived, blocked, and
invalid records.

`docs/release-promotion-rehearsal.contract.json` extends that authority to the
consumer wiring around Buildchain. Its side-effect-free rehearsal validates
alpha/stable positive and negative fixtures, immutable Buildchain locks,
release-passport evidence, and the dependency edge that prevents promotion
before Kungfu admission succeeds. It does not emulate Buildchain publication.
The v3 consumer baseline keeps that boundary intact while moving the stable
runtime and validation actions to Buildchain 3.0.0 and the promotion shell to
the corresponding v3 alpha contract.

The auditable demo is a consumer below the same boundary. It executes only an
exact retained installed artifact, requires the declared Buildchain Gate before
selective rendering, and binds the Gate and media roots into one Release
Passport. The README and downstream site may project that verified Passport,
but neither the demo nor first-party/System identity, KFD compliance, Product
System metadata, package metadata, registry history, scan output, or standalone
generation grants publication or runtime authority. Production deployment
remains a separate, explicitly authorized operation.

Multiple animations remain below that same boundary. A checked-in catalog
selects each demo by an explicit ID, direct argv, bounded completion contract,
scene identity, and publication metadata; the adapter does not invoke a shell.
PR 2454 projects that contract as three independent captures: Agent Work Lab
autoplay plus Project Tour episodes 1 and 2 at 1x, with each episode retaining
its own bounded completion sentinel and native-resolution evidence.
Release Passport v2 binds the selected demo, catalog root, descriptor root,
source revision, artifact digest, and media roots before README or site
projection. Exactly one catalog entry may be README-featured, so adding a
secondary qualified demo cannot replace the hero implicitly. Catalog
membership, first-party/System identity, KFD compliance, and Product System
assembly metadata remain non-authorizing facts; execution and publication
still require the exact Gate, Passport, Work/Warrant or Core policy, explicit
capability grant, and runtime isolation applicable to the operation.

Manual validation, Alpha promotion, and Release promotion compile into the same
retained source-bound trigger plan before invoking that Gate. Manual callers
may select Gate-only validation or full media rendering; Alpha and Release
always select the README-featured demo and full rendering. The plan grants no
publication authority, so automatic release-time media refresh does not
silently materialize README or site content.

Alpha promotion also consumes the exact successful development preflight
receipt for the immutable candidate before Buildchain receives publication
authority. Reuse remains bound to the source commit and tree, workflow and Gate
roots, dependency locks, toolchain and policy roots, and the complete platform
set. The promotion emits a source-bound timeline receipt through public
readback, keeps rehearsal data out of real release percentiles, and reports
low-sample SLO evidence explicitly.

PR [2444](https://github.com/kungfu-systems/kungfu/pull/2444) extends that
boundary with a stage-ready verification projection: upgrade source contracts
run once and are reused only by exact source and tree, full-product runtime
suites execute as a bounded two-wide dependency graph, and Gate plus invariant
verification may overlap only inside one active Shifu cache envelope. Every
platform retains independently rooted substage evidence and all started sibling
results; Linux ARM64 remains explicitly Core-only rather than claiming the
full-product runtime saving.

PR [2457](https://github.com/kungfu-systems/kungfu/pull/2457) extends Dev
delivery with a protected, fenced Warrant consumer. Native source qualification
is reusable only for the exact PR head and source tree; unrelated base movement
is classified separately, while merge-group admission still revalidates the
exact integration base before native queue entry. Shadow selection and terminal
closure produce lifecycle evidence without granting approval, publication,
branch-protection bypass, or paid-runner dispatch authority.

PR [2471](https://github.com/kungfu-systems/kungfu/pull/2471) promotes that
consumer from shadow evidence to required enforcement for targeted
`workflow_run` delivery. Manual dispatch and cadence patrol remain off, and the
same exact-head, native queue, terminal closure, and no-paid-runner boundaries
remain in force.

PR [2501](https://github.com/kungfu-systems/kungfu/pull/2501) closes a terminal
event-ordering gap observed on merged PR 2499: when GitHub delivers a
`dequeued` action whose pull-request payload already says `merged=true`, the
immutable merged fact wins. The consumer therefore cannot settle an actually
merged candidate as dequeued merely because the transient action arrived
first; exact candidate identity, required Warrant selection, and the existing
no-paid-runner boundary remain unchanged.

The diagnostic macOS overflow route remains below that publication boundary.
It prefers the healthy self-hosted lane, may start a GitHub-hosted candidate
after a trusted exact-label offline observation or a bounded queue or health
decision, binds both candidates to the same source and preflight, and forces
both to `publish-channel: none`. Its machine-readable receipt records route,
queue, runner, cancellation, result, and winner facts without gaining
promotion authority.

Normal native Buildchain matrices apply the same offline distinction to every
self-hosted platform lane independently. An online runner remains the selected
route even while busy; no matching online runner selects the platform's fixed
GitHub-hosted image; and an unavailable inventory API preserves the
self-hosted route. The immutable artifact-signing authority owns this routing
code, while Kungfu enables the policy and keeps the existing source,
qualification, signing, and publication boundaries.
Buildchain PRs
[2069](https://github.com/kungfu-systems/buildchain/pull/2069) and
[2071](https://github.com/kungfu-systems/buildchain/pull/2071) are the
cross-repository implementation and authority-promotion evidence.

The exact Alpha candidate branch is protected by a checked-in, root-bound
ruleset contract with no bypass actors, destructive updates disabled, and the
review and required-check policy verified by readback. Reusable cache decisions
are represented as structured, source- and toolchain-bound evidence rather than
inferred from cache logs. Completed release evidence is appended to a
content-addressed Git history so retention expiry cannot silently erase the
latency and SLO record; rehearsals and incompatible historical contracts remain
classified but cannot enter real Alpha percentiles.

Stable candidate selection reuses Buildchain's durable exact-version and
exact-SHA ledger instead of creating a second Kungfu state machine. The caller
records qualification completion, soak time, holds, revocations, explicit
`release-now` decisions, and the unique source-lock PR. Automatic selection may
open that PR, but cannot approve, merge, or publish it; stable ADR admission,
release qualification, protected review, and the existing Buildchain
publication transaction remain mandatory.

Version-line selection is data under
`framework/version-line/version-line-authority.json`. Branch and channel
templates, ruleset targets, candidate-ledger coordinates, runner routing,
publication surfaces, release metadata, and latency baselines are exact derived
projections of that authority. The source gate enumerates tracked Git sources
and fails closed when a concrete version-line operational setting is not an
exact admitted projection or a bounded compatibility alias. Synthetic v5 and
v6 fixtures prove that opening a later line changes authority data rather than
adding another branch-specific control path.

The gates establish process truth:

```text
dev:    declared bounded integration state
alpha:  qualified implementation-progress settlement
stable: no unaccounted accepted architecture obligation
```

They do not infer semantic fulfillment from filenames, commit text, or test
success. Reviewers still decide whether an implementation actually fulfills an
ADR and whether a waiver's residual risk is acceptable. The machine makes those
decisions explicit, scoped, and impossible to omit silently.

## Consequences

- Stable releases acquire a machine-auditable architecture balance sheet.
- Feature contributors make one bounded delivery declaration, but do not choose
  semantic versions or manually operate the release toolchain.
- Historical `unknown` implementation states become real release debt: they
  must be reconstructed, closed, or explicitly waived before stable.
- Alpha promotion PRs become the natural place to update implementation status
  accurately, because the complete development delta and full qualification
  result are both visible there.
- Release administrators accept named residual risk instead of bypassing a
  generic status check.
- The cost is one repository-local contract, validator, waiver ledger, and PR
  manifest. No service or mutable database is introduced.

## Alternatives considered

### Require every commit to reference an ADR

Rejected. Commit granularity is too small, mutable history weakens authority,
and unrelated fixes would produce low-signal ceremony.

### Update ADR status only after release

Rejected. This leaves development and alpha history under-specified and forces
maintainers to reconstruct progress after the evidence is dispersed.

### Let administrators bypass the stable check

Rejected. A bypass is neither scoped evidence nor a durable risk acceptance and
cannot appear honestly in the release passport.

### Require all proposed ADRs to be implemented

Rejected. A proposal is an open decision, not a product promise. Stable scope
begins when the decision is accepted.

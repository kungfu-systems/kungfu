# KF-ADR-019fb64f-ba63-7620-a384-063adec7af2f: Python KFX services use standard asyncio behind a journal bridge

- Status: accepted; implementation delivered by PR #2024
- Date: 2026-07-31

## Context

Kungfu historically exposed `LiveEventLoop` as a partial
`asyncio.AbstractEventLoop`. It constructed asyncio handles itself and reached
into private scheduling fields. That implementation could neither satisfy the
standard event-loop contract nor provide a stable compatibility surface across
supported CPython releases.

Two clocks and two execution modes must remain distinct:

- deterministic journal/replay processing is ordered by libkungfu journal
  frames, observed through RxCpp, and timed in journal nanoseconds;
- a live Python KFX service uses CPython's standard asyncio loop and its
  monotonic clock for tasks, futures, cancellation, timeouts, sockets, and
  subprocesses.

The earlier control-axis proposal
[KF-ADR-019f86da-4f90-7a30-8697-5c648120053d](KF-ADR-019f86da-4f90-7a30-8697-5c648120053d.md)
was withdrawn. This ADR is the required redesign decision; it does not reactivate
or silently amend that historical proposal.

## Decision

Python KFX services run in a separate interpreter process on CPython's standard
asyncio event loop. The TUI service host selects the Python bootstrap only from
an exact Core authorization, passes a minimal environment plus rooted
authorization metadata, and exposes exactly the declared capability relay.
Isolated placement applies the existing OS sandbox. Explicit integrated
placement remains a subprocess, but without the OS sandbox; it never moves
extension behavior into Core.

`JournalAsyncioBridge` coordinates a normal asyncio loop with a Kungfu reactor
using public APIs only. Journal callbacks enter with `call_soon` or
`call_soon_threadsafe`; coroutine results become ordinary tracked tasks. The
bridge never makes reactor time the asyncio clock and never makes asyncio time
the journal/replay clock. Journal frame ordering, RxCpp observation, replay,
and request/receipt semantics remain unchanged and Core-owned.

The service bootstrap requires `async run(caps)`. Its relay is non-blocking,
correlates concurrent calls, dispatches callbacks onto the asyncio thread,
wakes waiters if the host disappears, discards late results after cancellation,
and accepts a host shutdown control frame. Network, subprocess, and filesystem
writes are available only when the corresponding `network`, `process`, or
`storage` capability is granted. OS confinement and a Python audit hook form
defense in depth; unsupported or missing authority fails closed.

The normative machine-readable boundary is
[`python-kfx-asyncio-runtime.contract.json`](../qualification/python-kfx-asyncio-runtime.contract.json).
The supported interpreter range is `>=3.13,<3.14`.

## Consequences

Python KFX authors can use the supported asyncio ecosystem instead of a partial
event-loop imitation. Live service scheduling is standards-compatible, while
deterministic journal behavior keeps its existing authority.

`LiveEventLoop` remains temporarily as a source-level alias to
`JournalAsyncioBridge`; it is not an `AbstractEventLoop`. The alias may be
removed only after the first stable v4 Python KFX SDK line has no recorded
imports. Production code is gated against private asyncio scheduling fields and
manual `Handle` or `TimerHandle` construction.

The Python audit hook covers the supported standard-library ambient surfaces;
it is not a general-purpose in-process security boundary. Isolated services
therefore still require the OS sandbox, exact grants, minimal environment, and
the relay. Any new ambient surface needs an explicit capability mapping and
qualification before it is promised.

The falsifiable qualification includes bridge concurrency and clock separation,
async relay correlation/cancellation/closure, Python service tasks/futures/
timeouts/network/subprocess behavior, capability denial, graceful shutdown,
runtime-host authorization, and the pre-existing native KFX admission suite.

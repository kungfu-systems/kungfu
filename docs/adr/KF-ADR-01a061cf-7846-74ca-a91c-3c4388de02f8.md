# KF-ADR-01a061cf-7846-74ca-a91c-3c4388de02f8: PostgreSQL owns Assignment work transactions while Git owns code delivery

- Status: accepted; implementation staged
- Date: 2026-09-02
- Category: Work / Assignment / transaction authority / delivery
- Contract:
  [`assignment-runtime.contract.json`](../../framework/assignment-runtime/assignment-runtime.contract.json)

## Context

Ordinary code changes previously paid for two overlapping transaction systems.
The target repository carried code, review, and merge history while Atlas also
carried a goal card, checkpoint or ready marker, control-plane commit, ready
ref, and a separate command `2` merge. Git compare-and-swap protected those
Atlas files, but every small state transition became a repository edit and an
additional integration operation.

Kungfu Initiative and Assignment already own the actual work definition and
scope. A deployed PostgreSQL HA cluster can provide short row-level
transactions, version checks, lease fencing, append-only evidence, and exact
replay without turning each runtime state change into a Git branch. The
remaining architectural question is which system is authoritative for each
kind of fact and whether Atlas remains a fallback writer.

## Decision

### 1. Initiative and Assignment define the Work

An Initiative groups related intent. An Assignment is the executable unit and
owns the immutable work definition, including objective, scope, acceptance
criteria, and safety boundaries. Atlas Mission and legacy go records are not a
second business-work definition.

### 2. PostgreSQL is the single transaction authority

The `kungfu_work_control` database owns Assignment lease generation and token,
expiry, phase, version, checkpoints, evidence, completion, delivery, and the
append-only event history. Every mutation is one database transaction and
supplies `expectedVersion`. Mutations under a lease also supply its generation
and opaque token. The server serializes the Assignment row, checks the current
version and lease fence, applies the declared transition, and appends its event
atomically.

An identical command identity and payload replay returns the original receipt.
A reused command identity with different input, a stale expected version, an
expired lease, or an older lease generation fails closed. Clients do not infer
or reproduce phase transition rules.

### 3. Git remains authoritative for code delivery

The target repository continues to own code worktrees, commits, review, CI,
PRs, and the final merge commit. PostgreSQL records immutable Git coordinates
and verification evidence; it does not store source trees and does not replace
repository branch protection. Completion means the Assignment evidence is
accepted and the declared code change is complete. Settlement additionally
records the exact delivered Git ref or merge commit.

The ordinary sequence is therefore: select or create Assignment, acquire the
database lease, create the target repository worktree, modify and test, commit
and review through Git, record evidence and completion in PostgreSQL, merge in
Git, then record delivery and settle the Assignment.

### 4. Atlas is not a transactional fallback

An ordinary code Assignment does not create an Atlas worktree or update an
Atlas goal registry, checkpoint, marker, task ledger, ready ref, or command `2`
intake merely to express runtime Work state. Atlas may retain meta-rules,
historical legacy records, and explicit Atlas-repository deliverables, but it
must not shadow-write current Assignment state.

If PostgreSQL is unavailable or a version or lease check fails, the Work
transaction stops. It never falls back to Atlas Git files, local JSON, or a
client-side state machine. This preserves one writer and makes recovery read
from the Assignment database plus the target repository.

### 5. Clients are thin transports

The public Python client and CLI validate transport-shaped input, invoke the
registered PostgreSQL command, and return the server receipt. They may discover
the current HA primary but do not own transition policy, retry a rejected
compare-and-swap as a different command, print lease tokens, or persist secret
connection material.

## Consequences

- A checkpoint or phase transition no longer requires an Atlas branch, commit,
  ready ref, or control-plane merge.
- Row locks, versions, generation fencing, and idempotent command receipts make
  concurrent work inexpensive and independently auditable.
- Git retains the facts it is best at proving: source history, review, CI, and
  merge ancestry.
- PostgreSQL HA availability becomes a prerequisite for Work mutations. Read
  and code-repository operations may continue, but authority-changing commands
  fail closed until a primary is available.
- Existing Atlas-backed goals remain readable and can finish through their
  legacy path; they do not authorize new dual writes.

Rejected alternatives:

- **Keep Atlas markers as a mirrored fallback:** rejected because two writable
  authorities reintroduce reconciliation and ambiguous recovery.
- **Store code or PR state only in PostgreSQL:** rejected because it would
  duplicate Git and weaken normal review and branch-protection evidence.
- **Let clients implement transitions:** rejected because independently
  deployed clients would drift and could bypass the server's atomic invariant.
- **Use unrestricted table writes:** rejected because roles could mutate rows
  without the command contract, event append, or lease fence.

## Qualification and falsification

The staged implementation is qualified by contract validation, Python client
tests, Assignment runtime tests, source gates, and a live disposable-repository
exercise against the three-node PostgreSQL HA deployment. That exercise proved
one winner for concurrent same-version writers, stale-version rejection,
generation fencing, exact replay, evidence and completion recording, Git
fast-forward merge, delivery settlement, and standby convergence.

This decision is falsified if an ordinary code Work can mutate authoritative
phase, checkpoint, evidence, completion, or delivery state without the
PostgreSQL command contract; if stale or expired leases can write; if one
command identity can produce two effects; if Atlas files are required for a
normal Assignment transition; or if a client contains an independent phase
state machine. Cross-environment production evidence is still staged until the
PR's protected gates and merge complete.

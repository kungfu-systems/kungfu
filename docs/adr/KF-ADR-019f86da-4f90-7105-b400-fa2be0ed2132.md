## Context

Two schema-contract invariants are currently kept by human discipline, with no
mechanism catching a violation:

1. **`carrier_type` tag uniqueness.** Each POD type declares an explicit stable
   `tag` (e.g. `EpisodeOpen = 10801`) — the on-wire, cross-language, persisted
   type ID. Explicit stable IDs are correct here (like protobuf field numbers): a
   tag must not depend on declaration order, so it can never be auto-generated by
   an incrementing counter. But there is **no guard that two types don't share a
   tag** — a duplicate silently compiles (the registry map is keyed by type name,
   and the KF-ADR-019f86da-4f90-7a3d-9578-42b1c711759f `build_tag_set` sorts tags without a distinctness check).

2. **`carrier_type` → payload layout binding.** A frame's `carrier_type`
   dispatches its bytes to a specific POD struct layout (`decode_record_body`
   switches on `carrier_type` → `decode_v1_record<T>`). The manifest records carry
   a `schema_version` field, and the read path validates `payload_size >= sizeof(T)`
   and `schema_version <= known max` (a newer writer degrades to an unknown record,
   never bricks the reader). But that validates **size and version, not layout**.
   A size-preserving, version-unchanged layout change — reuse a field, an
   equal-width retype, a same-width reorder — passes both checks and is silently
   misread. This is the KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df "gap (1)" (the size-preserving hole), here for
   *payload* structs. KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df's compile-time fingerprint weld covers only the
   page/frame *container* header, not these payload records.

## Decision

Both invariants are welded at compile time, reusing the KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df layout
fingerprint and the KF-ADR-019f86da-4f90-7a3d-9578-42b1c711759f subset enumeration. No wire/POD layout changes.

1. **Tag uniqueness is a compile-time `static_assert`.** A constexpr check over
   the `AllTypes` roster asserts every `carrier_type` tag is distinct (reuse
   `build_tag_set`'s sorted array + an adjacent-distinct check). A duplicate tag
   fails the build. Tags stay explicit and hand-allocated — the machine guards
   them, it does not assign them (auto-increment would bind the ID to declaration
   order and break persisted/cross-language data).

2. **Payload layout is bound to `schema_version` by a paired `static_assert`
   (option B).** For each versioned manifest POD record, a `static_assert` binds
   `layout_fingerprint<T>()` (KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df) to a checked-in expected value tied to the
   type's current `schema_version`. Any layout change moves the fingerprint, fails
   the assert, and forces a deliberate acknowledgment — you cannot ship a
   layout change without touching the version binding.

   `schema_version` **stays an explicit, legible, hand-chosen integer — it is NOT
   derived from the fingerprint** (this is KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df's option B, which KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df
   correctly rejected for the *container* epoch but which is correct here).
   Rationale: unlike the machine-only container epoch, `schema_version` is
   read-dispatched and cross-version meaningful (the reader compares it to decide
   compatibility and to keep a newer version as an unknown record). Like the tag,
   it is a stable value consumed across versions, so it must not auto-derive.

3. **Staged strength — option i now, option ii before first stable release.**
   - **Option i (now):** one checked-in expected fingerprint per type. A layout
     change fails the assert; the developer updates the expected value and, by
     convention, bumps `schema_version`. This already closes the silent-drift bug
     (any layout change is caught).
   - **Option ii (at/before first stable release):** an append-only
     `{(type, schema_version) → fingerprint}` ledger. A released row may never be
     edited, so a layout change *forces* a new `(type, v+1, new_fp)` row plus a
     version bump — mechanically, not by convention. This matters only once
     released journals require multiple versions to coexist, mirroring KF-ADR-019f86da-4f90-7bf2-9789-1b88bf3ed265's
     staged compatibility and KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df's deferred-until-release converter.

## Scope

- The payload weld covers the **13 versioned manifest POD records** that carry
  `schema_version` — exactly the three KF-ADR-019f86da-4f90-7a3d-9578-42b1c711759f subsets: Episode manifest (6),
  source registry (3), manifest catalog (4). The weld enumerates them by reusing
  those derived subsets.
- **Version-less kernel/control types** (`Register`, `Config`, `Channel`, `Time*`,
  cache/band control, etc.) are out of scope: they carry no `schema_version` to
  pair to, and they are the runtime control plane, not persisted evolvable
  manifest facts. Whether they need their own protection is a separate question;
  the page/frame container headers are already welded by KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df.
- Tag uniqueness covers the whole `AllTypes` roster.

## Rationale

The tag and `schema_version` are stable external IDs; the layout fingerprint is a
derived internal check. The correct division is: **guard the explicit stable IDs
(tag, version) at compile time; derive and bind the layout fingerprint to them.**
This closes the payload-layer size-preserving hole and the missing tag-uniqueness
guard by turning two human-discipline invariants into build failures — reliability
over discipline, at zero runtime cost, reusing mechanisms already in the tree.

## Consequences

- A duplicate `carrier_type` tag, or a layout change to a versioned manifest
  record without touching its version binding, fails the build.
- `schema_version` remains a legible hand-chosen integer; the read-path
  size/version validation and graceful-unknown behavior are unchanged.
- Adding a versioned manifest type adds its expected-fingerprint entry; the tag
  uniqueness assert covers it automatically.
- No wire/POD layout change, no tag renumbering, no runtime cost.

## Alternatives considered

- **Auto-generate tags by an incrementing counter.** Rejected: the tag is a
  persisted, cross-language wire ID; an order-derived value breaks every historic
  journal and the cross-language mirror the moment a type is inserted. Explicit
  stable IDs are correct (protobuf field numbers). The machine guards uniqueness;
  it does not assign.
- **Derive `schema_version` from the fingerprint (KF-ADR-019f86da-4f90-741b-8f16-b27fcd99d0df option A).** Rejected
  for payloads: `schema_version` is read-dispatched and cross-version meaningful,
  so it must stay explicit and stable — the opposite need from the machine-only
  container epoch.
- **Option ii ledger now.** Deferred: pre-stable-release there are no released
  journals to protect (KF-ADR-019f86da-4f90-7bf2-9789-1b88bf3ed265 allows breaking cleanups), so option i already
  catches the bug at lower cost. Option ii becomes load-bearing at stable release.
- **Read-time layout validation instead of a compile weld.** Not chosen as the
  primary: for a closed POD set the reader and writer share one binary per
  version, so the residual hole is purely a compile-time discipline failure, best
  caught at compile time at zero runtime cost. (The existing read-time size/version
  checks stay as the cross-version guard.)

## Verification

- A build-time check: a duplicate tag fails the uniqueness assert; a layout change
  to a versioned manifest record fails its fingerprint assert; a matching layout
  compiles.
- Feasibility proven by spike: `layout_fingerprint<T>()` computes for all 13
  versioned manifest records (distinct fingerprints), the paired assert compiles,
  and the tag-uniqueness assert holds over `AllTypes`.
- Full build + tests green (the registry feeds projections, state cache, bindings).

## Replacement Criteria

A replacement design is acceptable only if it preserves:

1. compile-time detection of a duplicate `carrier_type` tag;
2. compile-time detection of a versioned manifest record's layout changing without
   a deliberate version-binding change;
3. `carrier_type` tags and `schema_version` remaining explicit, stable,
   order-independent values (never auto-derived);
4. a path to option ii (forced version bump on released data) at stable release.

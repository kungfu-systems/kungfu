# KF-ADR-019f86da-4f90-713b-a44c-0677d2446cc1: Storage backend changes are authority-atomic, resumable operations

- Status: accepted; staged for the embedded file and optional RocksDB providers
- Date: 2026-07-18
- Category: runtime storage / authority / recovery
- Related: [KF-ADR-019f86da-4f90-70c5-b572-89ec183b37de](KF-ADR-019f86da-4f90-70c5-b572-89ec183b37de.md),
  [KF-ADR-019f86da-4f90-738c-b372-e509976f69ff](KF-ADR-019f86da-4f90-738c-b372-e509976f69ff.md), and
  [KF-ADR-019f86da-4f90-7ec5-a83c-99cfaee56aca](KF-ADR-019f86da-4f90-7ec5-a83c-99cfaee56aca.md)

## Context

Kungfu can select either the dependency-free content-addressed file provider or
the optional RocksDB provider behind one C++ storage service. Selection alone is
not migration. Changing an option or `KUNGFU_STORAGE_PROVIDER` for a populated
runtime can otherwise make already admitted content disappear from the selected
view, while two processes may continue writing different physical stores.

Journal catalogs remain backend-neutral authority and SQLite remains a
rebuildable projection. The backend-dependent material is the immutable content
store, including every valid namespace such as `payloads` and `schemas`.

## Decision

### 1. One binding decides the active provider

`storage/backend-binding.json` is the provider authority for a populated
runtime. It records the provider, monotonically increasing generation, semantic
root, committed object and byte counts, previous provider, operation identity,
and commit time. The file is published by atomic replacement only after target
verification succeeds.

Until a binding exists, an empty runtime may use the requested provider with no
migration ceremony. A legacy runtime with content in exactly one provider is
read through that inferred provider. A requested option or environment value
that disagrees with a binding or unambiguous legacy content fails closed and
routes the user to `kungfu storage backend switch`.

### 2. Switching is a resumable state machine

`storage/backend-switch-state.json` records one backend-neutral operation with
these phases:

1. `copying`: inventory and copy immutable objects while the old provider stays
   authoritative and writable;
2. `cutting`: fence old-provider writes, perform the final incremental copy,
   verify every authoritative object and semantic root on the target;
3. publish the new binding atomically;
4. `committed`: retain the old provider read-only and publish a receipt.

Crashes before binding publication leave the old provider authoritative. A
rerun resumes the same idempotent content-addressed copies. A crash after binding
publication observes that operation identity in the binding and finishes the
receipt without reverting authority.

`storage/backend-switch.lock` serializes operations across local processes; a
contender fails with `backend_switch_busy` instead of creating a second state
machine. The lock is coordination metadata, not authority: the atomic binding
remains the only provider commit point. Normal provider writes hold a shared
`storage/backend-authority.lock` from authority check through publication. The
final cut takes that lock exclusively before it publishes `cutting`, so it waits
for already-admitted local-process writes, blocks new ones until the binding is
committed, and then lets them retry against the new generation. An in-process
recursive mutex closes the same boundary between local threads.

### 3. Rollback is the same operation in reverse

Rollback does not merely restore a configuration value. It first copies every
object admitted to the current provider since the prior cut back to the retained
provider, enters the same write-fenced cut, verifies parity, and atomically
publishes a new generation. Neither direction deletes provider data.

### 4. All product surfaces share the C++ operation

The typed C++ storage contract owns backend status, switch, rollback, state,
binding, inventory, verification, and receipts. Python and Node expose the
existing JSON edge over those operations; CLI, GUI, and agents must consume that
same edge rather than implement provider migration themselves.

## Falsification and acceptance gates

- file to RocksDB and RocksDB to file preserve all namespaces and bytes;
- a fault during copy resumes without changing the binding prematurely;
- a pre-cut verification failure leaves the old provider authoritative;
- restart after binding publication resolves only the new provider;
- a manual provider mismatch on populated storage fails closed;
- rollback reverse-copies post-switch objects before its own atomic cut;
- concurrent writes are either included by the final copy or retry after the
  brief cut fence, with no acknowledged object lost;
- a second process cannot start another switch while the operation lock is held;
- a cross-process write holds the shared authority lock through publication and
  the exclusive final cut waits for that writer before changing generations;
- a build without RocksDB reports `provider_unavailable` and never publishes a
  target binding;
- every fixture uses a temporary runtime root; no qualification touches a real
  user data home.

## Consequences

Readers resolve either the old or new authority from one atomic binding, never a
partially copied hybrid. Writers may continue during bulk copy, are briefly
rejected during the final cut, and cannot write the retained old provider after
commit. Receipts expose source and target profiles, counts, bytes, generations,
pre/post semantic roots, verification, and residual rollback boundaries.

This decision is single-host and embedded-provider scoped. It does not claim
cross-machine consensus, distributed writer fencing, destructive source cleanup,
or physical-media durability beyond each provider's declared capabilities.

# KF-ADR-019f87cc-bd45-7a5c-9b37-1d6b5917928a: Assignment claim separates Owner, Agent, Slot, and Lease

- Status: accepted; implementation and qualification staged
- Date: 2026-07-22
- Category: Work Control / delegation / execution authority
- Related: [KF-ADR-019f86da-4f90-7626-861e-3fdee887abd2](KF-ADR-019f86da-4f90-7626-861e-3fdee887abd2.md) and
  [KF-ADR-019f87cc-bd1f-786d-896d-07ea9245861e](KF-ADR-019f87cc-bd1f-786d-896d-07ea9245861e.md)

## Context

An agent name, account slot, and task authorization answer different questions.
Conflating them lets possession of a runtime slot look like authority to claim
work, obscures who bears responsibility and cost, and leaves abandoned claims
unbounded.

## Decision

An Assignment execution claim records four distinct identities:

- **Owner** is the accountability and cost principal.
- **Agent** is the acting runtime identity.
- **Slot** is an execution lane and grants no authority by itself.
- **Lease** is the bounded authorization for this task and slot.

Every claim also records `authorized_by`, `grant_scope`, and an ISO-8601
`lease_expires_at`. The run gate requires a still-active lease. Expired claims
remain evidence but grant no continuing execution authority. Public records
must not carry credentials, account tokens, private quota state, or secret host
inventory.

## Falsification and qualification

This decision is false if a claim omits any identity, accepts an expired or
timezone-free expiry, treats a slot as authority, passes the run gate after
expiry, or serializes private credential material.

## Consequences

- Claim responsibility can be audited independently of execution placement.
- Lease expiry gives recovery a deterministic fail-closed boundary.
- Identity-pool implementations may remain more restrictive without changing
  the public Assignment fact vocabulary.

# ADR-0082: C++23 + Rx is the core language strategy

- Status: accepted (the language increments it prescribes are staged — see
  "Staged adoption")
- Date: 2026-07-14
- Category: architecture — core implementation language and expressiveness
  strategy
- Subsystem: `framework/core` (libyijinjing, libkungfu)
- Related: [`docs/development/rust-adoption.md`](../development/rust-adoption.md)
  (the Rust option paradigm; fixes "the memory-safety core stays C++" as a hard
  boundary — this ADR argues the *expressiveness* dimension that document
  deliberately leaves open);
  [ADR-0046](ADR-0046-rust-host-trunk-and-assembled-runtime.md) (Rust owns the
  process host and control plane; this ADR is its complement for the core);
  [ADR-0065](ADR-0065-schema-registry-consolidation.md) and
  [ADR-0067](ADR-0067-schema-registry-compile-time-contract-welds.md) (the
  registry-level exhaustiveness machinery this ADR ratifies as the canonical
  pattern);
  [ADR-0001](ADR-0001-yijinjing-publish-barrier.md) (the single-writer
  journal discipline the whole argument stands on).

## Question

Should the core stay C++23 + Rx as it keeps growing features, or does Rust's
language expressiveness — `Result` + `?` error propagation and exhaustive
`match` over closed sum types — compound into an advantage that would justify
migrating core code?

Scope: language expressiveness and code complexity only. Toolchain ergonomics,
runtime performance, and memory safety are governed elsewhere (memory safety by
architecture confinement plus fuzzing, per `rust-adoption.md`; the host
topology by ADR-0046) and are not arguments in this record.

## Context

The core is a single-writer, deterministic, single-threaded event-loop runtime:
every process owns its journal exclusively, all state transitions replay from
recorded frames, and concurrency between processes is mediated by the journal
rather than by shared mutable memory. That architecture — not the
implementation language — is what eliminates data races and the complex
ownership graphs that Rust's borrow checker exists to police.

Against that background the recurring migration argument reduces to two
residual language features plus one under-counted asset:

1. Rust's `?` makes fallible call chains terse and makes failure modes visible
   in signatures.
2. Rust's exhaustive `match` guarantees at compile time that no variant of a
   closed sum type is left unhandled.
3. The under-counted asset: the core's Rx layer
   (`framework/core/src/libkungfu/include/kungfu/runtime/rx.h`) is not a
   dependency detail but a routing algebra whose expressiveness must be part of
   any honest comparison.

An audit of the current core (2026-07) established the facts this decision
stands on:

- Error handling today is exceptions end to end (no `std::expected`, no
  monadic `optional` use anywhere in the core), funneled through one
  subscriber-boundary collector (`loop_error_state`, rx.h) that records the
  first error, stops the loop deterministically, and rethrows outside it.
  A second style exists at durability seams: hand-written `catch` ladders that
  translate exception types into error-code enums plus status structs
  (`durable_ingest.cpp`), and a third, value-returning early-return style in
  pure scan paths. Three styles, no written policy.
- The message-type universe is a compile-time closed Hana roster
  (`schema/registry.h`): category subsets are derived from one membership
  table instead of hand-listed (ADR-0065), member counts are pinned by
  `static_assert`, and versioned records are welded to layout fingerprints
  through an intentionally undefined primary template, so an unregistered type
  is a compile error (ADR-0067). Uniform dispatch is generated by
  `hana::for_each` over those sets, so adding a type extends every uniform
  consumer by construction.
- Dispatch sites in the live layer are Rx chains — one tag per line, composable
  source/dest filters, temporal operators (`skip_until` registration
  handshakes, `take_until` start gating, `first()` one-shots), and domain
  timers that travel through journal time (a `TimeRequest`/`Time` round trip),
  making timeouts replayable events rather than wall-clock threads.
- Compiler warnings are `-Wall` / `/W3` with no `-Werror`: a missed enum case
  in a `switch` without `default` warns but does not fail the build.
- C++23 is pinned (`CMAKE_CXX_STANDARD 23`, conan `cppstd=23`), yet several
  C++23/20 expressiveness features the comparison hinges on are unused:
  concepts (constraints are all `enable_if` SFINAE), `std::expected`,
  deducing this, and ranges beyond three predicate algorithms.

## Decision

1. **The core stays C++23 + Rx.** No Rust migration of core code is planned or
   held open as a pending question; the Rust option remains exactly where
   `rust-adoption.md` and ADR-0046 place it (process boundaries and the host
   trunk, never hot-path FFI).
2. **Error handling becomes a written three-tier policy** instead of three
   accidental styles:
   - *Non-recoverable* (protocol violation, corrupted journal, invariant
     breach): throw; the Rx subscriber boundary and `loop_error_state` are the
     single classification point; crash-only plus journal replay is the
     recovery mechanism.
   - *Classify-and-continue seams* (durability barriers, ingest boundaries,
     external input validation): `std::expected<T, E>` with monadic
     composition; exception-to-enum translation happens once per seam in a
     `transform_error` classifier instead of hand-written `catch` ladders.
   - *Pure scan paths* (offline readers, reconciliation): value-style early
     return with explicit error codes, preserving honest `Unknown` semantics.
3. **Registry-level exhaustiveness is the canonical pattern** for every type
   family: closed Hana roster, membership-table derivation, count
   `static_assert`s, and undefined-primary-template coverage welds. New
   families do not hand-list subsets or scatter per-site checks.
4. **True sum types use `std::variant` + `std::visit`** with a complete
   overload set (the `changelog_payload` precedent), which is compile-time
   exhaustive; visitation gaps are a build failure, not a convention.
5. **Staged language increments** (see below) close the remaining per-site
   gaps with configuration and incremental migration, not a language switch.

## Rationale

**The architecture filter comes first.** Rust's headline guarantees target
shared-state concurrency and complex ownership. The single-writer runtime has
neither: migrating would buy guarantees the architecture already provides,
while paying a full rewrite of load-bearing, fuzz-qualified code — and
cross-process mmap sharing is `unsafe` in Rust anyway, so the risk would move,
not disappear.

**Error propagation.** Under a single event loop with crash-only semantics,
exceptions plus one boundary collector need *zero* per-call annotation, versus
one `?` per call and one `Result<>` per signature in Rust. Rust's real residual
advantage is signature-level legibility of failure modes, which matters at
seams where callers genuinely branch on failure classes — and the policy adopts
`std::expected` exactly there. What C++ cannot fully replicate is implicit
error-type conversion (`From` + `?`); `transform_error` keeps that cost to one
explicit classifier per seam, which does not grow with feature count.

**Exhaustiveness.** In an event-routing architecture, per-site totality is the
wrong requirement: reactors intentionally subscribe to a subset of the event
universe, and the equivalent Rust `match` would carry a wildcard arm — which
disables the exhaustiveness check it is being credited for. Where totality is
the real requirement ("every type in family S has X"), the registry machinery
already enforces it at compile time, in one place, for all consumers — a
stronger position than per-site checks. The remaining per-site gap (a missed
case in a small-enum `switch`) is a warning-level diagnostic today and becomes
a build failure with `-Werror=switch`; that is a configuration debt, not a
language deficit.

**The Rx algebra is a net advantage, not a compensation.** Routing composes
over three axes (carrier type, source, dest) with variadic alternatives —
one-dimensional `match` needs nested guards for the same selection. Protocol
phases (registration handshake, start gating, replay end-of-time) are
declarative one-liners over the event stream; the Rust-native equivalents are
either an async-stream runtime (exactly the scheduler nondeterminism this
runtime exists to exclude) or hand-rolled state flags. Domain timers travel
through journal time, so timing behavior replays deterministically — a property
neither language provides and the Rx layer already packages.

**Growth curves stay linear on every observed feature axis** (new event types,
new record families with projections, new reactors, new protocol phases). The
single axis where Rust holds a small edge — error-classification seams — is
linear, one-time-per-seam, and shrinks under the `expected` policy. The heavy
compile-time machinery (Hana registry, reflection base) is a paid fixed cost;
the marginal cost of a new type is one roster line plus handlers, matching a
Rust `derive` attribute.

## Alternatives considered

- **Migrate the core to Rust.** Rejected. The borrow checker's problem domain
  is architecturally absent; the Rx temporal algebra would have to be
  reconstructed on an async runtime the design forbids, or degraded to manual
  state flags; the rewrite would forfeit years of fuzz corpus and qualification
  evidence on load-bearing code; and hot-path FFI seams are excluded by
  `rust-adoption.md`.
- **Adopt `std::expected` wholesale.** Rejected. Under the loop-boundary model
  it strictly increases annotation weight (monadic chains at every fallible
  call) for zero behavioral change on non-recoverable paths — a worse position
  than either current style.
- **Record no policy.** Rejected. The three-style drift in error handling is
  observable today and is precisely the kind of unbounded divergence this
  record exists to stop; unwritten conventions do not survive contributor
  turnover.

## Staged adoption

The ratified baseline is already on mainline — the compile-time registry and
its welds (PR #660), and the Rx loop-error boundary with local stop ownership
(`a296e6dfd`) — which is what the implementation evidence above points at. The
increments below are the pending stages, in dependency order, each shippable
independently:

1. Promote `-Werror=switch` in the compile contract
   (`.cmake/compiler.cmake`); audit the three storage-layer `switch` sites and
   keep deliberate `default` arms only where unknown inputs are a designed
   state (`source_registry_unknown_record` stays).
2. Write the three-tier error policy into `CONTRIBUTING`-adjacent developer
   docs; convert the durable-ingest `catch` ladders to `expected` +
   `transform_error` as the reference implementation.
3. Migrate SFINAE constraints to concepts incrementally, starting with the
   `data<T>` accessor overloads (`common.h`) and the registry `copy()` pair —
   highest-traffic diagnostics first. No flag-day.
4. Opportunistic: deducing this where CRTP is boilerplate; ranges where the
   `reader.cpp` TODO already points.

## Re-evaluation triggers

Reopen this decision if any of the following is observed, rather than on
sentiment:

1. Recoverable-error taxonomies exceed roughly ten enums with genuine
   cross-layer composition needs, and the seam-classifier pattern is visibly
   failing to contain translation boilerplate.
2. The core protocol type universe must become open at runtime (plugin-defined
   protocol types), breaking the closed-roster premise. (The existing custom-
   event channel already carries opaque user types without touching the
   roster; this trigger is about *protocol* types.)
3. RxCpp maintenance cost trends upward — the carried patch count grows beyond
   the current two, or a supported compiler breaks it unrecoverably. The used
   operator surface is small (filter/first/take_until/skip_until/merge plus
   the domain operators in one 263-line header), so vendoring or replacing the
   backend is a bounded fallback to evaluate at that point, not a rewrite
   argument.
4. Template diagnostics in the Hana-heavy zones measurably dominate
   contributor rework after the concepts migration has landed.
5. C++26 lands pattern matching (P2688) and static reflection (P2996) in the
   supported compiler matrix — reopen not to reconsider the language, but to
   retire the reflection macros and close the destructuring gap this record
   honestly leaves open until then.

## Consequences

- Positive: the recurring "should the core be Rust" question gets a recorded,
  evidence-based closure with observable reopen conditions; error handling
  gains a written policy where today there is drift; the registry
  exhaustiveness pattern is ratified as canonical rather than folklore; the
  cheap parity wins (`-Werror=switch`, concepts) get an ordered adoption path.
- Negative / accepted residuals: destructuring pattern matching stays absent
  until P2688; error-type composition stays explicit (`transform_error`) where
  Rust's `From` is implicit; Hana-zone template diagnostics remain a real tax
  until the concepts migration lands; RxCpp 4.1.1 remains a watched,
  patch-carrying dependency.
- The staged increments touch developer-facing configuration and internal
  seams only; no public API or product behavior changes are implied by this
  record.

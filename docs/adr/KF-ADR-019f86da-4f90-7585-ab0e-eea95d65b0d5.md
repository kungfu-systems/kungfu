## Context

KF-ADR-019f86da-4f90-7ec5-a83c-99cfaee56aca defines `visible`, `durable_group`, `durable_sync`, and later
`replicated` as distinct promises. The current-hardware program has admitted a
default-off single-host production candidate for the first three profiles, but
users previously had no KFD-1 configuration contract that could select them or
carry their cost and failure policy into the standard runtime.

A loose preference such as `durable=true` would collapse important
distinctions. It could not state whether the request is per fact or per group,
which qualification evidence authorizes it, how long a caller waits, what an
unknown outcome means, or whether a workspace may be stricter than a user
default. Treating the config value itself as qualification would be worse: a
JSON edit would become a durability claim.

## Decision

### 1. The config records a request, never a qualification claim

The registered `config-contract` owns `storage.durability` and a canonical
policy digest. Its public states are deliberately separate:

- **requested** is the recursively merged KFD-1 value;
- **admission** is the current runtime's evidence-bound verdict;
- **effective** is the policy the runtime will actually execute, or `refused`.

`activation=qualified-candidate` asks to use the named candidate. It does not
set `qualification_passed`, widen `production_eligible`, or change any
capability non-claim. Python projects the capability report for early
diagnostics; libkungfu independently re-derives admission from its compiled
authority, the candidate evidence identity, contract hash, policy digest, and
fail-closed limits. Product bindings do not accept a caller-supplied
qualification boolean.

### 2. Scope is defaults, then user, then workspace

The user override remains `${KF_CONFIG_HOME}/config.json`. A workspace may add
`.kungfu/config.json`. Objects merge recursively; scalars and arrays replace.
The workspace value wins so one project can require stronger treatment without
silently changing every other project on the machine. Resolved output names
every source and publishes the `storageDurability` digest.

### 3. Profile selection is deterministic and bounded

The policy has one `defaultProfile` plus ordered matching rules over carrier
type, source id, and destination id. All fields present in a rule must match.
The winner is highest priority, then lexical rule id. Public configuration may
select only `visible`, `durable_group`, or `durable_sync`; `replicated` remains
unavailable.

Every strong request must use `qualified-candidate` activation. A strong
default or rule with activation off is refused as a whole; it is never silently
downgraded to `visible`.

### 4. Every tuning value has one runtime owner

- `segmentMaxBytes` controls KFDL segment rollover after a completed barrier.
- `requestTimeoutMs` becomes the absolute deadline on a barrier request.
- `reconcileOnTimeout` controls immediate request-id reconciliation after a
  timeout or unknown receipt.
- `group.maxRecords`, `group.maxBytes`, and `group.maxDelayMs` bound
  `durable_group` batching. Crossing any bound flushes the latest frontier.
- `failurePolicy` is fixed to `fail-closed` in v1.

`durable_sync` performs an immediate barrier. `durable_group` returns pending
until a threshold or explicit flush earns a receipt. A timer error is retained
for inspection and cannot manufacture an acknowledgement.

### 5. The standard coordinator owns the execution chain

The resolved native policy is passed when `CoordinatorEngine` constructs the
libkungfu coordinator. Its in-process state-service remains the sole data-root
write authority. A configured stream acquires the existing OS-backed writer
lease, opens one stream epoch, appends through that fence, and requests or
reconciles receipts through the state-service. Public code does not receive the
service object or a mutable qualification seam.

Returned execution envelopes bind the config contract hash, policy digest, and
qualification profile to the selected profile and native receipt. The durable
checkpoint remains the native receipt authority. The policy envelope explains
which current configuration caused the request; it does not rewrite historical
checkpoint bytes or claim that a later config was active for an older receipt.

### 6. Timeout remains an unknown-outcome protocol

A deadline may stop work before barrier I/O starts. Once I/O has started,
expiry may produce `unknown`; cancellation cannot prove rollback. When enabled,
automatic reconciliation queries the exact request id and position. If that
still returns unknown, the caller must retain the original identity and
reconcile after reopen. Retrying with a new id is not an acceptable substitute.

## Compatibility and KFD-1 classification

This is config contract version 3. It is an additive pre-release update to the
registered `config-contract`: existing overrides omit `storage.durability` and
inherit safe defaults. Workspace overrides are newly recognized. Resolved
output gains a digest and source entry. Before v4 stable no prior version is a
compatibility root; later changes to precedence, profile meaning, receipt
semantics, or required identity require the ordinary KFD-1 decision process.

## Rejected alternatives

### Let config set `qualificationPassed`

Rejected because editable input cannot be evidence. Native admission must
re-derive the verdict.

### Silently fall back to visible

Rejected because a caller asking for durability would receive a weaker promise
under the same successful startup path.

### Make every fact durable_sync

Rejected because it imposes a device and metadata sync on every selected fact,
often reducing throughput and increasing tail latency without improving facts
that are reconstructible.

### Put batching only in application code

Rejected because config would advertise thresholds that the standard runtime
did not execute consistently.

## Consequences and non-claims

- Users gain one inspectable policy across Python, Node/KFX config consumers,
  CLI, assembled artifacts, and the coordinator runtime.
- Strong policy startup can now fail when contract identity, evidence, limits,
  or profile support disagree. This is intentional.
- Group batching adds a small timer and pending-memory cost per active stream;
  sync profiles add filesystem/device barrier cost.
- This decision does not add HA, replication, consensus, independent failure
  domains, or physical-power-loss qualification. The current capability remains
  a production candidate and `production_eligible=false`.

## Implementation and qualification

The contract, Python/TypeScript resolution, CLI inspection, native admission,
standard coordinator wiring, fenced stream execution, batching, timeout
reconciliation, and targeted tests are implemented by
[PR #845](https://github.com/kungfu-systems/kungfu/pull/845). The implementation
is qualified through local Shifu source checks and Core builds on macOS arm64
and agent-120 Linux x64, plus native receipt/recovery and Python policy tests.

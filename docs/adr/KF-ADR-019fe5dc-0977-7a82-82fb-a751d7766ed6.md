# KF-ADR-019fe5dc-0977-7a82-82fb-a751d7766ed6: Agent sessions are independent from Work lifecycle

- Status: accepted; implementation staged
- Date: 2026-08-09
- Category: Agent Session / Work Control authority boundary
- Supersedes: the single delegated-Work binding clause of
  [KF-ADR-019f86da-4f90-7977-9cfc-85d26d41780b](KF-ADR-019f86da-4f90-7977-9cfc-85d26d41780b.md)

## Context

The native Agent integration persisted one `workBinding` on a
`SessionAttempt`. After an Agent completed one Assignment, binding a second
Assignment in the same provider process failed with
`attempt_work_binding_mismatch`. The only escape was to terminate the provider
and create another session.

The Work `claim` and `kickoff` CLI paths also called Agent Session Work binding
before performing their native Work Control action. An ended or unavailable
`SessionAttempt` therefore rejected an otherwise valid Work transition with
`attempt_not_active`. This was a direct Work-to-Agent-Session lifecycle
dependency, not merely a restrictive Agent adapter behavior.

That behavior joined two independent lifecycles. An Agent session describes a
provider process, transport, recovery, and interaction state. An Assignment is
a Work Control authority object whose admission, execution, review,
continuation, closeout, and portable seal are defined without an Agent session.
Requiring a new provider process for another Assignment made Work progress
depend on an implementation detail and created a high-friction false boundary.

## Decision

### 1. Session identity contains no Work identity

`WorkConsole`, `SessionAttempt`, Capsule, and provider child identify the Agent
runtime chain. `WorkRef` is not a parent in that identity chain. A session may
carry an optional current Work observation for onboarding, UI projection, and
runtime-local coordination, but that observation is not Assignment authority.

### 2. A live session may replace its current Work observation

Binding another exact `WorkRef` in the same live attempt atomically acquires the
new Work-keyed runtime lease, releases the prior lease held by that attempt,
replaces the current observation, and discards the prior Work projection. The
provider process and `SessionAttempt` continue unchanged.

The replacement does not require or imply that the prior Work is terminal. It
does not mutate, abandon, complete, reopen, or seal either Assignment. Those
transitions remain exclusively owned by Work Control actions and evidence.

### 3. Single-writer protection remains Work-keyed

A different live attempt still cannot acquire an exact Work that already has an
active Agent lease. The switch checks the destination conflict before releasing
the source lease, so a denied switch preserves the original association. After
a successful switch, another Agent may acquire the prior Work.

### 4. Session receipts make no Work claim

Bind and switch plans keep `workEffects` empty. Session receipts prove only the
runtime association change. Provider exit, session recovery, or association
replacement cannot prove Work outcome or alter retained Work facts.

### 5. Work actions never require Agent Session state

Assignment admission, claim, execution advance, stage, review, continuation,
closeout, and seal do not call Agent Session APIs and do not inspect
`WorkConsole` or `SessionAttempt`. A delivery workflow may separately start an
Agent and publish an optional Work observation, but that ordering belongs to
the Agent implementation. It is not a precondition in the Work model.

## Consequences

- One Codex, Claude, Amp, or OpenCode process can execute successive
  Assignments without restart.
- Work lifecycle remains usable and authoritative without any Agent Session
  runtime.
- Ambient, ended, missing, or provider-specific SessionAttempt state cannot
  reject a valid Work claim or kickoff.
- Existing registry data remains readable. The singular `workBinding` field is
  retained as the current observation, not an immutable lifetime binding.
- A switch clears stale projection data so one Assignment cannot appear under
  another WorkRef.
- The decision is false if a second Work requires a new `SessionAttempt`, if a
  Work action calls Agent Session state, if a session transition changes
  Assignment state, or if two live attempts can simultaneously hold the same
  exact Work lease.

## Evolution Stage: ambient current-process adoption (2026-08-13)

A provider process that was started outside the Kungfu launcher may adopt one
observer-only native Console when all of the following coordinates are exact:

- a public provider thread identifier parses as a UUID;
- a live ancestor process has the exact provider executable name;
- the process identifier and process start time are available from the public
  operating-system process table; and
- the current directory resolves to one qualified Kungfu Project.

The semantic root of those current-process coordinates determines the native
attempt identity. The product either reuses the matching attempt or registers
it through the existing native start and heartbeat operations. Adoption reads
no provider authentication state, private session database, private logs, or
terminal bytes. A missing, malformed, mismatched, or unqualified coordinate
fails closed.

The adopted Console has no bootstrap mutation authority. Bootstrap may remain
pending because the provider process was not launched through the bootstrap
protocol. `bind-work` only replaces the optional Work observation, retains an
empty `workEffects` set, and does not authorize any Work transition. Admission,
claim, kickoff, execution gates, review, and closeout remain independent Work
Control actions with their own exact authority and evidence.

# KF-ADR-019f9ec5-fa5d-76a3-9adb-71611ee67005: Product caches live outside immutable artifacts under one versioned cache home

- Status: accepted; implemented and qualified by PR #1633
- Date: 2026-07-26
- Category: product runtime — disposable cache ownership
- Subsystem: Desktop, the installed CLI, native trunk launch, and product staging

## Context

Python imports normally create bytecode. A signed application bundle is an
immutable release artifact, so writing `__pycache__` or `.pyc` into its bundled
runtime changes the signed tree after ordinary GUI or CLI use. Disabling
bytecode writes avoids that mutation but discards a useful runtime cache and
does not establish a reusable home for future disposable product state.

Workspace state (`KF_HOME`), product configuration (`KF_CONFIG_HOME`), and
disposable caches have different ownership and retention. A selected workspace
must not silently become the destination for interpreter caches, and a cache
must be safe to delete without deleting facts, configuration, or installed
artifacts.

The product release manifest already supplies `runtimeBuildId`, an identity for
the exact assembled runtime. It is therefore the correct namespace boundary for
cache entries whose validity depends on shipped runtime bytes.

## Decision

Kungfu defines `KF_CACHE_HOME` as the single root for disposable product
caches. Resolution is deterministic, in this order:

1. an explicit, non-empty `KF_CACHE_HOME`;
2. `<KF_INSTANCE_HOME>/cache` when an instance home is explicit;
3. the native per-user cache location:
   - macOS: `~/Library/Caches/kungfu`;
   - Windows: `%LOCALAPPDATA%\Kungfu\Cache`;
   - Linux: `${XDG_CACHE_HOME:-~/.cache}/kungfu`.

Python bytecode lives at `KF_CACHE_HOME/python/<runtimeBuildId>` through
`PYTHONPYCACHEPREFIX`. Released Desktop and CLI surfaces bind
`runtimeBuildId` from the colocated upgrade manifest. A source-tree runtime
without a manifest uses the explicit `development` namespace. A supplied but
missing, malformed, or unsafe manifest fails closed instead of collapsing
different release caches together.

The native `kungfu-trunk` launch boundary is authoritative because every
installed Python command passes through it. Desktop resolves and exports the
same contract before spawning children so Electron-owned processes observe one
cache root. Shell launchers only bind the colocated manifest; they do not
disable bytecode or independently invent a cache path.

Product staging and Electron packaging exclude `__pycache__` directories and
all `.pyc` files. Signed/read-only artifacts remain immutable during ordinary
use; writable bytecode is generated under the external, versioned cache.

## Consequences

- Python keeps its normal bytecode performance without mutating a signed app,
  CLI runtime, source checkout, or selected workspace.
- The root can later contain sibling namespaces such as `cache/python` without
  treating Python as the product-wide cache contract.
- Runtime upgrades receive separate cache namespaces. Stale namespaces are
  disposable, but this decision does not authorize automatic deletion or
  define cache-retention policy.
- An explicit `KF_INSTANCE_HOME` intentionally keeps disposable state inside
  that isolated instance. An explicit `KF_CACHE_HOME` remains the highest
  precedence override for tests, managed installations, and operators.
- Precompiling every `.pyc` was rejected because interpreter flags, optimization
  levels, import paths, and writable extensions can still require runtime
  caches. Shipping bytecode would also enlarge and complicate the signed tree.
- Whole-product Nuitka conversion was rejected: it changes distribution,
  extension, debugging, and compatibility boundaries but does not remove the
  need for a general disposable cache root.
- The decision is falsified if normal packaged GUI/CLI use changes any bundle
  byte, creates bytecode inside a selected workspace, or cannot create bytecode
  under `KF_CACHE_HOME/python/<runtimeBuildId>`.

# KF-ADR-019f9f8a-9f40-7d6e-a4d2-5a334a9ab201: stable KFX service and webhook host v1

- Status: accepted
- Date: 2026-08-10
- Scope: provider-neutral long-running service lifecycle and authenticated
  webhook ingress

## Decision

Freeze `kungfu.kfx.service-host/v1` as an additive public KFX contract.
`config.service.host` declares bounded lifecycle, listener, opaque credential
handles, and intake limits. Core owns the state machine, authority enforcement,
broker boundary, and receipts. KFX code owns provider authentication semantics,
normalization, and domain effects.

No listener exists by default. Loopback and non-loopback listeners require
separate exact capability evidence. Credential bytes remain inside an approved
host broker. Dynamic dependencies are active only while installed, qualified,
authorized, and compatible. Package identity or origin has no decision input.

This ADR is also the normative author/host reference. The schema is embedded in
both shipped copies of `kungfu-kfx.contract.json`; the executable
host is `KfxServiceWebhookHost`; the retained v1 corpus is under
`framework/api/tests/fixtures/kfx-service-webhook/v1`.

## Public manifest

`kungfu.kfx.json` remains the only KFX manifest authority. A v1 webhook
service adds `config.service.host`:

```json
{
  "schema": "kungfu.kfx.manifest/v1",
  "name": "@example/local-webhook",
  "version": "1.0.0",
  "kungfuConfig": {
    "key": "example-local-webhook",
    "config": {
      "service": {
        "runtimes": ["node"],
        "entry": { "node": "service.mjs" },
        "capabilities": ["network.listen", "credential.verify"],
        "host": {
          "schema": "kungfu.kfx.service-host/v1",
          "contractVersion": 1,
          "lifecycle": {
            "restartPolicy": "on-failure",
            "readinessTimeoutMs": 5000,
            "drainTimeoutMs": 5000,
            "shutdownTimeoutMs": 5000
          },
          "webhook": {
            "listener": {
              "mode": "disabled",
              "path": "/events",
              "methods": ["POST"]
            },
            "credentials": [{
              "handle": "credential:webhook/signing",
              "purpose": "webhook-signature-verification",
              "algorithms": ["hmac-sha256"]
            }],
            "intake": {
              "maxPayloadBytes": 1048576,
              "maxQueueDepth": 64,
              "maxInflight": 8,
              "maxRequestsPerWindow": 120,
              "rateWindowMs": 60000,
              "handlerTimeoutMs": 5000,
              "replayWindowMs": 300000
            }
          }
        }
      }
    }
  }
}
```

`disabled` is the safe default and declares no address or port. Enabling a
loopback listener requires an explicit `bindAddress`, `port`, and exact
`network.listen` plus `credential.verify` grants. A non-loopback address
uses `mode: "explicit"` and additionally requires
`network.listen.non-loopback`. A service cannot widen either grant by editing
its manifest.

The executable public types and state machine are exported from
`@kungfu-tech/api/capability` as `KfxServiceWebhookHost`,
`KfxServiceHostDeclaration`, `KfxCredentialBroker`, and
`KfxWebhookHandler`.

## Authority and dependency admission

A host may start only when all six authority roots are canonical
`sha256:<64 lowercase hex>` values and their evidence is current: KFD
qualification, Work Warrant, release or incubation Passport, host
authorization, exact capability grant, and the dynamic dependency set.

Every dynamic dependency must also be installed, qualified, authorized, and
version-compatible. A missing or revoked condition produces `dormant`; it
never falls through to ambient authority. Restoring all four conditions returns
the service to `installed`, from which a fresh start is required.

## Lifecycle and receipts

The public states are `installed`, `dormant`, `starting`, `ready`,
`draining`, `stopped`, `crashed`, `deactivated`, and `uninstalled`.

| Operation | Valid source | Result |
|---|---|---|
| `start` | installed, stopped, eligible dormant | starting, new generation |
| `ready` | starting | ready |
| `drain` | ready | draining; new intake is refused |
| `stop` | starting, crashed, or drained with zero inflight work | stopped |
| `crash` | starting, ready, draining | crashed |
| `restart` | stopped, crashed | starting, new generation |
| `upgrade` / `rollback` | installed, stopped, deactivated | installed at the exact evidenced version |
| `deactivate` | installed, stopped, dormant | deactivated; volatile intake state cleared |
| `uninstall` | installed, stopped, deactivated, dormant | uninstalled; volatile intake state cleared |

Every operation returns `kungfu.kfx.service-host-receipt/v1` with sequence,
generation, version, outcome, stable diagnostic, exact authority roots, and a
canonical receipt root. Receipt details never carry request bodies, headers,
signatures, broker errors, or credential values. The dependency root makes
revocation and restoration decisions auditable without embedding provider data.

## Webhook intake

An admitted host evaluates one request in this order:

1. ready lifecycle and enabled listener;
2. current KFD/Warrant/Passport/authorization/capability/dependency evidence;
3. method and exact path;
4. payload size, rate window, replay window, and inflight/queue bounds;
5. signature presence;
6. broker verification using the declared opaque handle and algorithm;
7. KFX-owned normalization with the handler deadline;
8. KFX-owned domain callback.

Steps 1–6 happen before the domain callback. Broker exceptions collapse to
`KF_KFX_WEBHOOK_AUTHENTICATION_FAILED`; their text is not retained. Provider
code receives a verification operation, never the credential value.

```ts
const host = new KfxServiceWebhookHost(
  declaration,
  exactAuthorityEvidence,
  credentialBroker,
  {
    credentialHandle: 'credential:webhook/signing',
    algorithm: 'hmac-sha256',
    async normalize(request) {
      return normalizeProviderEvent(request); // KFX-owned
    },
    async onEvent(event) {
      await applyDomainEffect(event); // only after accepted authentication
    },
  },
);
```

Stable refusals cover contract/lifecycle, qualification/authorization,
dependency dormant, listener policy, unsupported method/path, unsigned,
authentication failed, replayed, oversized, rate exceeded, queue full, timeout,
and normalization failed. Exact names live in `nativeRuntime.errors` and the
exported `KfxServiceDiagnosticCode` type.

## Compatibility

The outer KFX contract advances additively from version 13 to 14; native KFX
documents remain `native-contract/v3`. Existing service declarations stay
readable but cannot activate the v1 webhook host until they add a complete
`host` declaration. Incompatible v1 evolution requires a new schema identifier,
qualified migration, retained old reader, and rollback.

## Rejected alternatives

- Raw secrets in manifests or service environment: rejected because they leak
  into portable and diagnostic surfaces and create ambient authority.
- Trust by first-party key or install origin: rejected because equal evidence
  must receive equal decisions.
- Default or implied listener binding: rejected because installation is not
  network consent.
- Provider authentication in Core: rejected because it moves domain behavior
  into the platform and forces provider release coupling.
- A second service lifecycle or capability authority: rejected because KFX
  already has native admission, Warrant, Passport, capability, and Fact/Cut
  owners.

## Consequences

Downstream authoring and reference suites can target one installed public
contract without reading source. Platform adapters still have to transport HTTP
requests into the seam, and provider packages still have to implement their own
normalizers. Neither task may bypass the stable host decisions.

The installed product now carries a deterministic authoring kit for this
contract: the `kfx authoring` CLI, brief, machine-readable contract, generated
SDK, and offline webhook-service template. Its scaffold, build, package,
inspect, validate, and qualify operations produce inputs and evidence only;
they do not install, activate, authorize, bind a listener, or grant credential
or domain-action authority.

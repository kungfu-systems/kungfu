# KF-ADR-019f86da-4f90-7b1a-8633-b9153e586424: Product diagnostics are one read-only projection over existing authorities

- Status: accepted; implemented
- Date: 2026-07-16
- Category: product diagnostics / runtime / storage / Episode
- Related: [KF-ADR-019f86da-4f90-7667-b89e-18b1002e45f8](KF-ADR-019f86da-4f90-7667-b89e-18b1002e45f8.md),

  [KF-ADR-019f86da-4f90-7bc8-a3ed-a7b0a6363d6c](KF-ADR-019f86da-4f90-7bc8-a3ed-a7b0a6363d6c.md),

## Context

Kungfu already exposes machine-readable runtime status, fenced Peer lifecycle
status, typed storage status and fsck, and Episode inspection and recovery plans.
Those surfaces preserve their own authority boundaries, but a user must know
their topology and technical vocabularies before deciding whether ordinary work
is safe. Separate UI translations would drift and could accidentally turn a PID,
a derived projection, or an incomplete recovery observation into authority.

A first-use workspace also creates an important product constraint: an absent
resident runtime is normal for daemonless storage work. A generic service probe
must not call that condition unhealthy or create state merely to inspect it.

## Decision

### 1. One contract owns the diagnostic projection

`framework/core/runtime/kungfu-diagnostics.contract.json` registers the
`product-diagnostics-contract` welded surface. It freezes:

- `kungfu.health-report/v1` and `kungfu.diagnostic.problem/v1`;
- `ready`, `degraded`, `action-required`, and `blocked`;
- exit codes 0, 1, 2, and 3 in that order;
- a shared actionable problem catalog;
- fast/deep coverage and read-only guarantees.

Each problem retains the underlying `sourceCode`. The user message and actions
are a projection; they never replace the runtime, Peer, storage, or Episode
technical error contract.

### 2. Existing components remain authoritative

The runtime check consumes `kungfu.runtime.status/v2` and the topology-neutral
product status. Peer diagnostics consume the fenced lifecycle status. Storage
diagnostics consume the typed service status and fsck result. Episode
diagnostics consume the manifest fold, writer ownership inspection, and the
existing recovery planner.

Diagnostics do not reimplement lifecycle transitions, storage verification, or
recovery eligibility. GUI, CLI, and agents may render the same report, but no
renderer may promote its local process or file observations to readiness.

### 3. Fast and deep are observational modes

Fast mode is the default. It bounds Episode inspection to 100 records and never
invokes storage fsck. Deep mode is explicit and adds the complete read-only
storage integrity scan and all open-Episode recovery plans.

Neither mode starts, stops, restarts, or signals a process; repairs a route;
rebuilds or applies a projection; writes an Episode terminal record; or runs a
suggested action. The root CLI callback also skips runtime-directory
initialization for `health`.

### 4. Unknown outcomes fail closed

A live PID without matching process-start identity, unknown Episode writer
liveness, unknown Episode age, an unrecognized manifest record, or a failed
diagnostic collector is `blocked`. It is never translated into “safe to retry”
or “safe to recover.” Suggested commands stop at inspection, fsck, or a dry-run
plan and never contain `--execute`.

### 5. Daemonless and intentionally stopped are healthy states

An absent first-use runtime directory, an inactive product runtime, and a Peer
whose desired state is stopped are not failures. A stale resident route may be
degraded, while an ordinary live-required operation retains authority to
activate the runtime through the existing activation contract.

### 6. Automatic preflight is command-scoped and never authoritative

High-value activation and write commands select a named profile from the same
diagnostics contract. Each profile declares its runtime, Peer, storage, or
Episode areas; command-level freshness; whether facts may be cached; and the
allow, warn, or block policy for every health status. The initial profiles are
fresh and uncached. They always use fast collectors and never invoke deep mode.

Ready is silent. A non-ready result is rendered once through the shared problem
catalog, and only a problem in a declared area can affect that command.
Inspection, status, health, contract, and help surfaces do not receive an
automatic full-health scan. Recovery commands may warn and continue so their
existing planner or execution fence remains the final authority.

The preflight observation does not close a time-of-check/time-of-use window.
Runtime activation, Peer host control, and Episode/storage writes retain their
fresh generation, ownership, or writer fence at the execution point. Cached
facts may not replace those fences in a future profile.

## Falsification and acceptance gates

- a fast health test fails if storage fsck is called;
- before/after file fingerprints must match for first-use, fast, and deep health;
- a stale open Episode may offer only a recovery plan, never execution;
- unknown writer or process identity must produce exit 3 and non-retryable
  problems;
- contract checks reject destructive or `--execute` suggested actions;
- profile checks reject deep mode, cached facts, undeclared areas, or missing
  status policies;
- ready command preflight is silent and an irrelevant collector is never run;
- a write-point fence can still reject after a ready preflight;
- the portable Mac qualification covers cold/warm empty and initialized
  workspaces plus four concurrent shells, with cold p95 <= 250 ms and warm p95
  <= 100 ms for incremental preflight and validation;
- Linux, macOS, and Windows full-profile CI build Core and run the same unit and
  native read-only fault matrix;
- existing command JSON and technical error codes remain unchanged while plain
  error output gains actionable translation.

## Consequences

Users gain one stable preflight and machines gain deterministic JSON and exit
codes. The cost is that new technical errors which should have specialized user
guidance must be added to the shared catalog; unknown codes remain visible as
`sourceCode` but deliberately fall back to a blocked generic problem.

The first scoped-profile qualification observed a maximum cold p95 of 8.82 ms
and warm p95 of 4.72 ms on Mac, including four concurrent worker processes.
That evidence does not justify a
generation-aware fact cache or single-flight coordinator. The design keeps
those mechanisms absent until a real authority surface exceeds the budget;
shrinking a profile's areas remains the first optimization.

Automatic repair and a guided recovery wizard remain separate future product
work. This decision supplies their read-only evidence and action descriptions,
not authorization or execution.

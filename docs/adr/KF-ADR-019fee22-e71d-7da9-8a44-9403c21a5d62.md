# KF-ADR-019fee22-e71d-7da9-8a44-9403c21a5d62: Kungfu Skill v2 is a content-rooted Work-scoped orchestration contract

- Status: accepted and implemented; the contract, canonical registry and
  lifecycle fold, thin surface bindings, native KFX/Profile admission, compact
  Agent decision advisory, bounded workspace-local instruction-only authoring,
  and deterministic qualification are retained, while later effectful authoring
  and multi-surface runtime waves remain outside this cut
- Date: 2026-08-11

## 2026-08-15 terminal qualification projection

PR 3122 retains one exact-cut terminal qualification for the implemented Skill
v2 product boundary. The retained manifest binds the protected source cut, the
installed lifecycle result, the six-outcome Agent decision surface, bounded
fault and recovery evidence, and the reconciled family state. Its verifier
replays those roots without upgrading local platform evidence into a public
release, adoption, stability, or marketplace claim. The local installed
artifact qualifies `darwin-arm64`; Linux and Windows remain explicitly
unqualified by this cut.

The retained evidence is historical input to verification, not a second Skill
registry, lifecycle authority, or Work completion authority. Work selection,
continuation, acceptance, and completion remain governed by the existing native
contracts described below.

## Amendment boundary

This decision amends the original
[Kungfu Skill context-layer decision](KF-ADR-019f86da-4f90-74c2-9cbb-24f1c34303bf.md)
without retiring its load-bearing separation: a Skill remains an agent-facing
object above separately governed KFX packages. The amendment replaces only the
underspecified Skill identity, class, scope, lifecycle, dependency, proof, and
recovery model. Existing v1 documents remain historical inputs; they do not
acquire v2 meaning merely because a newer reader exists.

## Context

The first Skill contract proved a useful context loop: a `SKILL.md`-only source
can become a compact catalog entry, be loaded on demand, bind KFX package keys,
and appear through Python, Node, managed-run, and Skill Manager projections.
That implementation deliberately used a small model: one source-file hash,
first-root-wins discovery, two classes (`instruction-only` and `kfx-backed`),
and sidecar-oriented audit.

That model cannot safely carry the next product layer. A directory can contain
undeclared files while retaining the same `SKILL.md` hash. The same key has no
immutable revision coordinate. `kfx-backed` combines operational behavior and
domain semantics. Scope and Work selection are implicit. Capability requests,
external effects, proof, recovery, compatibility, and historical meaning are
not one contract. A Skill could therefore look reusable while its full content,
authority dependencies, or effect boundary remain ambiguous.

Meanwhile, Core now owns a native KFX registry, trust and capability admission,
and lifecycle. Domain Profile contributions have their own authoring,
qualification, and lifecycle authority. Work, Fact, Episode, KFD, and KFX must
not be copied into Skill merely to make the Skill model complete.

## Decision

### 1. Identity is a stable key, immutable revision, and complete content root

The canonical v2 coordinate is:

```text
skill key + monotonically increasing revision + complete content root
```

The content root commits to the normalized, sorted closure of every packaged
member, including `SKILL.md`; a single-file hash is not a v2 package root.
Producers must reject path escape, duplicate members, missing entrypoints,
undeclared payloads, root mismatch, and attempts to bind one key and revision
to different content. A later revision preserves its predecessor coordinate and
must not reinterpret old bytes.

### 2. Scope and Work binding are explicit

Every definition declares a distribution scope and whether Work binding is
optional or required. Work remains the selection, continuation, acceptance,
and completion authority. Catalog advertisement, UI focus, loading full
instructions, provider output, or a successful process exit does not select a
Skill for Work and cannot complete Work.

### 3. There are exactly three Skill classes

- **instruction-only** contains rooted instructions and no executable
  dependency, capability request, or external effect;
- **operational** references at least one exact admitted KFX dependency and
  requires the KFX capability and invocation path for every effect;
- **domain** references at least one exact admitted Profile contribution and
  may additionally reference KFX. Profile owns domain meaning; KFX owns
  executable behavior.

Skill content may describe, request, and orchestrate those dependencies. It
does not copy their payloads, grant capabilities, activate lifecycle state, or
become their authority.

### 4. Effects, proof, recovery, and compatibility are contract fields

Effectful Skills enumerate each effect and bind it to a declared exact
dependency. `effects.mode = none` is incompatible with capability requests.
Every Skill carries explicit proof requirements, completion ownership, and
recovery steps. Compatibility names the v2 contract, predecessor coordinate,
runtime requirements, and the rule that historical roots, receipts, Work
bindings, and meaning are preserved.

### 5. Lifecycle vocabulary is shared, but lifecycle state is not stored in the definition

The one vocabulary is:

```text
authored -> validated -> installed -> enabled -> selected -> loaded -> invoked
                                             \-> suspended -> retired -> historical
```

These terms name distinct observations. A definition contains only lifecycle
policy. The later registry fold owns current state, generation, plans, receipts,
and history. No manager, provider Skill, GUI, Agent self-report, package prose,
or KFX manifest may create a second Skill lifecycle.

### 6. Explicit non-authority is part of every definition

The v2 schema requires non-claims for Work, Profile, Fact/Episode, KFD, KFX,
capability, completion, and historical interpretation. These are machine
contract fields, not optional documentation. The deterministic contract check
also rejects incomplete roots, mutable identity, undeclared dependencies,
class/capability mismatch, hidden effects, ambiguous scope, history rewrite,
and duplicate authority claims.

## Consequences

- The v1 source, catalog, context, dependency, and manager schemas remain
  readable during staged migration. They are not silently upgraded.
- Registry and lifecycle implementation must consume this exact v2 definition
  contract and keep previous roots replayable.
- KFX and Profile integration must resolve exact references through their own
  admission authorities. A Skill-local copy or prose grant is invalid.
- Agent recommendation and authoring may use the contract, but draft,
  validation, installation, enablement, Work selection, and invocation remain
  distinct decisions.
- The Agent decision advisory may select only one rooted recommendation from
  bounded signals; it cannot capture Work, write or install a Skill, invoke
  KFX, change Profile meaning, grant capability, or mutate an external system.
- Multi-surface clients must project one registry and history rather than
  mutate directories directly.
- This decision is falsified if implementation needs a second lifecycle writer,
  accepts the same key/revision with two roots, permits an instruction-only
  capability, invokes an undeclared dependency, or changes the meaning of a
  historical Work record after a Skill update or retirement.

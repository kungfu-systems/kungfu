# SHIFU-ADR-019fab1a-2853-737e-8c67-a9b1aa9035aa: Qualified Assignment Core artifacts bind identity, qualification, and promotion authority

- Status: accepted; contract merged in PR #1808, exact producer/promotion delivery merged in PR #1836, hosted runtime activation independently reviewed in PR #1840, automatic source consumer delivery proposed in PR #1889, bounded usage observability merged in PR #1930, native compatibility identity proposed in PR #1934, bounded cold-path transport proposed in PR #1944 after PR #1942 was superseded to preserve linear Project Cut replay, Linux x86_64 consumer qualification proposed in PR #1981, pinned uv activation repair proposed in PR #1984, Windows x86_64 consumer qualification proposed in PR #1990, and exact Windows runtime-closure verification proposed in PR #2019
- Date: 2026-07-30

## Context

Assignment Core builds are expensive enough to reuse, but a transport cache hit
does not prove that native bytes belong to the current source, platform, Python
ABI, toolchain, dependency lock, or protected delivery candidate. Rewriting
producer metadata to look current would erase the distinction between exact
identity and an independently established equivalence. Copying payloads
directly into a runnable target also leaves traversal, symlink, partial-write,
and dirty-checkout ambiguity.

The contract must remain useful when cache providers are unavailable. GitHub
Actions cache and workflow artifacts can disappear, be evicted, or be replaced
without changing the correctness of a merge. Shifu, Buildchain, CAS,
Assignment, qualification, and promotion therefore need explicit and
non-overlapping responsibilities.

## Decision

Shifu defines strict versioned JSON schemas under `docs/shifu/schema/`: one
qualified Assignment Core artifact manifest and one qualification receipt per
major contract. V2 is the producing contract; retained exact-commit v1 objects
remain readable only through the same verifier through 2026-10-31 and cannot
enter compatibility-index reuse; after that boundary they fail closed to a
current-source build. All objects reject unknown fields and
unsupported major versions. Roots are
SHA-256 over UTF-8 JSON with recursively lexicographic object keys, original
array order, `JSON.stringify` scalar encoding, and no insignificant whitespace.

The manifest binds:

- producer repository, commit, and source-tree root;
- target repository and commit;
- exact native input, operating-system, architecture, Python ABI, build
  profile, toolchain, and dependency-lock identities;
- versioned Shifu and Buildchain contract roots;
- a sorted, unique set of regular files and safe relative symlinks with exact
  path, size, digest, and mode;
- the manifest, artifact, qualification, and promotion-authority roots; and
- clean-checkout, outside-target staging, atomic replacement, and
  non-runnable-partial-state requirements.

Exact mode requires producer and target commits to be identical. Explicit
equivalence requires distinct identities plus an immutable equivalence receipt;
producer metadata is never rewritten. The qualification receipt rebinds the
manifest and artifact roots, records all mandatory checks as passed, and binds
one active, time-bounded authority for the exact protected-development target.
Missing, stale, or ambiguous promotion authority fails closed.

V2 separates exact revision provenance from native compatibility. Its
compatibility root commits to the complete tracked `framework/core` closure,
platform, architecture, CPython ABI, exact toolchain identity, dependency
locks, build profile, Shifu and Buildchain contract roots, the manifest and
qualification policy implementation, and the payload root. It intentionally
excludes commit id, full repository tree, branch, timestamp, and path
similarity. A producer and protected target may differ only when independent
recomputation yields the same compatibility root; the equivalence document
retains both exact commits and trees.

Shifu owns schema, canonical roots, verification, and safe publication
semantics. Buildchain supplies exact build and delivery identities. Assignment
supplies producer and target intent. CAS retains verified bytes by content root.
Qualification proves one manifest/payload pair. Promotion authority selects
one currently reusable candidate. Cache and workflow artifacts transport bytes
only and never establish identity, qualification, or promotion authority.

## Consequences

Consumers can reject tampered payloads, traversal, unsafe symlinks, platform or
ABI drift, build/toolchain/lock drift, dirty targets, producer impersonation,
and stale or ambiguous selection before publication. Cache loss or rejection
falls back to a current-source build, so transport availability cannot affect
merge correctness.

The producer/promotion slice seals the minimum relocatable macOS ARM64,
CPython 3.13 Assignment Core runtime closure (`kungfubuildinfo.json`, one
`pykungfu` binding, one versioned `libnode` dylib, and
`libkungfu_runtime.dylib`) from an exact merge-group run after affected-native
qualification and promotes it only for the exact protected-development target.
Its workflow artifact remains replaceable transport, and rejection or absence
continues to select the current-source build.

The producer uses three collision-free CPython
3.13 rows: macOS ARM64, Linux x86_64, and Windows x86_64. The
matrix binds each row to an exact hosted runner identity, build-information
identity, dependency/toolchain facts, and minimum native payload closure.
Candidate and promoted names bind source commit plus row. Promotion selects at
most one authority per row and emits an indexed qualified/unqualified result;
missing rows remain source-build fallbacks, and cross-row substitution is
forbidden. Automatic consumption is admitted for all three rows. Intel macOS
is explicitly unsupported product-wide and cannot enter source-build fallback;
the prior four-row strategy is retained only in immutable Git and Assignment
history, as amended by KF-ADR-019fbbe4-40c5-7c67-9ed2-910a65430ff7.

On macOS ARM64 source checkouts, `./shifu work` may now resolve an exact or
compatibility-qualified protected workflow artifact, independently reverify
the native closure, platform,
CPython ABI, toolchain, dependency locks, Shifu and Buildchain contract roots,
qualification, validity, and the single protected promotion authority, retain
it in a user-local content-addressed store, and atomically publish the runtime
closure into this checkout. Existing or mismatched targets are never
overwritten. Miss, expiry, ambiguity, tamper, or identity drift produces one
machine-actionable `./shifu build:core` fallback; no consumer path replaces or
modifies an installed Kungfu application. The local index is keyed by
compatibility root rather than commit, while every materialization receipt
retains the producer commit, protected qualified target, and exact consuming
checkout. Protected promotion may republish a previous object only after
current-source compatibility verification and only when no second distinct
compatible authority is active. The delivery does not claim cross-platform
qualification or authority to make transport availability a blocking build
path.

On Linux x86_64 CPython 3.13 source checkouts, `./shifu work` enters the same
consumer before declaring the current checkout unbuilt. Protected promotion
qualifies a fresh explicit Linux bundle in one detached checkout, verifies the
ELF runtime closure and executable modes, activates Work Control, and then
qualifies a second detached checkout from the retained immutable local CAS with
GitHub transport disabled. Both observations retain exact receipt roots while
remaining optimization evidence only. Linux ARM64 and every other Python ABI
remain explicit unsupported-host fallbacks.

On Windows x86_64 CPython 3.13 source checkouts, `shifu.cmd work` invokes the
same verifier before declaring the checkout unbuilt and may reuse the
repository-pinned `uv` executable from Shifu's local tool cache. Build metadata
records normalized `windows` and `x64` identity independently from the native
OS-version diagnostic so variable Windows version strings cannot decide
qualification. A protected bundle materializes only the declared PYD, DLL, and
build metadata closure on a Windows hosted runner, where every native payload
is rechecked as a PE image and `shifu.cmd work` executes against the published
runtime. A second detached checkout then reuses the retained immutable local
CAS object with GitHub transport disabled. Identity drift, unavailable
authority, and verification failure retain the machine-actionable
current-source build fallback without registry, service, scheduled-task,
firewall, installed-product, or global-Python writes.

The minimum Windows native closure is exactly one
`pykungfu.cp313-win_amd64.pyd` binding plus `libnode.dll`; build metadata is
verified separately. Hosted consumer qualification requires both named files
and rechecks each as a PE image. It does not infer completeness from a minimum
file count, because the qualified artifact contract already closes the exact
manifest and a count threshold can reject the valid two-file runtime.

Work activation resolves the repository-pinned `uv` binary from Shifu's native
tool cache when a fresh runner does not expose `uv` on `PATH`. Resolution binds
the checked-in pin, normalized host target, regular-file identity, and
executable mode; unsafe pin segments and unavailable tools retain the existing
machine-actionable source-build fallback. This repair adds no download,
credential, global configuration, or alternative artifact authority.

Each consumer attempt may also publish one immutable, bounded observation under
the Qualified Core cache root and expose a read-only summary through
`./shifu qualified-core status --json`. These records preserve selected result,
reason, duration, source, compatibility, platform, and artifact identities
across worktree removal while excluding paths, provider bodies, signed URLs,
credentials, and raw environment state. They remain optimization evidence only:
an observation cannot qualify, promote, admit, claim, or authorize an artifact.

After trusted GitHub workflow discovery establishes the unique artifact,
successful protected run, source commit, and workflow path, the consumer may
obtain the exact artifact bytes from a configured office HTTP endpoint. That
endpoint is replaceable transport only. Transfers are streamed under an exact
declared-size bound, resume only from artifact-identity-bound partial state and
an exact `Content-Range`, restart from byte zero when Range is ignored, and
never publish partial runnable state. Completed staging is removed after
successful verification or archive and verification rejection. The retained
Darwin ARM64 reference evidence attributes discovery, transfer, verification,
retention, and publication separately across three cold and three retained-CAS
runs without retaining the endpoint.

The hosted runtime activation keeps the aggregate machine job identifier
expression-safe so the exact merge-group macOS ARM64 producer is actually
scheduled. A completed run with fewer than both required transport artifacts
remains an unavailable producer and selects the source-build fallback; multiple
candidate or delivery artifacts remain ambiguous and fail closed. The machine
identifier is therefore `affected_native`, while its human-visible required
context remains `affected-native / linux`; downstream `needs` expressions use
the identifier-safe machine name. The producer condition begins with
`always()` so exact proof reuse may skip heavy indirect prerequisites without
preventing evaluation of the successful direct aggregate dependency. The
hosted producer also declares the bounded Buildchain source-build environment,
which uses the existing Conan bootstrap contract to detect a default profile
only when a fresh runner does not already have one.

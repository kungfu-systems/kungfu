# KF-ADR-019f86da-4f90-7a57-a680-9739f5e67173: Kungfu centers the product loop on Project Cut

## Context

Kungfu now has a precise lower model for admitted state, causal occurrence,
direction, perspective, authority, work claims, independent assessment, and
continuation. Exposing all of those objects as peer product concepts would make
the implementation visible without giving an ordinary user one stable answer
to the question that matters: what the project is now, and what changed after
the agent worked.

Mission and Go have proved that persistent work organization matters. Project
Cut has proved that source, Atlas, and Episode authorities can be bound without
collapsing them. The final product shape should use both lessons while reducing
the default interaction to one repeatable settlement loop.

## Decision

### 1. Project Cut is the highest ordinary product interface

The primary product loop is:

```text
current Project Cut
  -> bounded Agent Work
  -> candidate next Project Cut
  -> explicit verification and settlement
```

A Project Cut is the project-level commitment presented to users and agents.
It binds lower authorities and discloses omissions, conflicts, and residual
risk. It does not become source authority, Atlas authority, Episode authority,
or a second Fact ledger.

### 2. Initiative and Assignment organize work between cuts

The Agent Work Domain Profile uses two primary work terms:

- **Initiative**: a continuing body of intended project change; and
- **Assignment**: a bounded unit of accepted responsibility that can be
  executed, assessed, and continued.

They project the lower Pursuit, Atlas, and Warrant responsibilities into
software-work language. They remain above Action Geometry and may not redefine
Fact or Episode authority.

Mission and Go remain the current compatibility projection. This ADR does not
rename persisted objects, protocol tags, roots, or public commands. A later
cutover must be a versioned KFD-1 migration with exact mapping, retained
readers, differential evidence, and rollback.

### 3. Lower objects use progressive disclosure

Fact, Episode, Pursuit, Atlas, Warrant, Claim, Assessment, and Decision remain
independently inspectable and machine-addressable. Ordinary users need not
operate them as peer top-level concepts. Product surfaces reveal them when
work becomes consequential, ambiguous, delegated, stale, conflicted, or under
review.

Convenience may reduce interaction count. It may not merge responsibilities,
invent authority, or hide a degraded basis.

### 4. `kungfu cut` is the primary command group

`kungfu cut` with no mutating option is a read-only project summary. It may
report the current cut, active Initiatives and Assignments, pending candidate,
and actionable problems. It must not create a data root, write runtime state,
advance a ref, accept a Claim, or settle a Project Cut.

Preparation, verification, and settlement are distinct operations. Every
authority-changing operation requires explicit intent, a previewable plan, a
typed receipt, and post-operation verification. The GUI, TUI, CLI, and agent
interfaces project the same operations and evidence.

### 5. v4 release requires the complete loop

The v4 product is not release-ready merely because each lower primitive can be
queried. A clean installation must demonstrate, through public interfaces:

```text
inspect current cut
-> accept bounded work
-> preserve execution as admitted Episode evidence
-> submit and independently assess the completion claim
-> settle the next cut
-> continue from that exact cut in a fresh agent context
```

The release gate must also prove read-only defaults, failure visibility,
cross-surface semantic parity, independent verification, and portable exact
continuation.

## Consequences

- The most common user interaction can remain small even as the kernel becomes
  more rigorous.
- Initiative/Assignment management and Project Cut management become explicit
  product layers rather than incidental views over lower objects.
- Project Cut becomes the integration point for source, context, runtime
  evidence, trust decisions, and continuation without owning any of them.
- Existing Mission/Go and `./shifu project-cut` surfaces remain valid
  implementation inputs, not the final public product hierarchy.
- Product work must optimize time-to-first-cut and cut-to-cut continuity, not
  the number of primitives exposed in the interface.

## Rejected alternatives

### Expose every primitive as a peer user concept

This preserves implementation detail but transfers the system's coordination
cost to the user and gives no project-level closure.

### Keep Mission/Go as the final highest-level product

Persistent work organization is necessary, but a maintained task graph does
not by itself state what project state has been accepted after work occurred.

### Let Project Cut absorb its bound authorities

This would create a competing truth source and weaken independent verification,
replay, migration, and recovery.

### Make `kungfu cut` mutate by default

Read-only inspection is a dual-first safety boundary. Implicit creation or
settlement would make exploration carry authority-changing side effects.

## Qualification

The decision is satisfied only by the executable contract in
[Project Cut Product Loop Qualification](../qualification/project-cut-product-loop.md).
The current `project.cut/v1` protocol and settlement implementation are
prerequisites, not evidence that the product loop or v4 release gate is already
complete.

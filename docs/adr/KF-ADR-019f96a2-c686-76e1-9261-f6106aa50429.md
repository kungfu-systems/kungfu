# KF-ADR-019f96a2-c686-76e1-9261-f6106aa50429: Portable format authority is a composition contract

- Status: accepted; authority composition, required-reader, migration/repair, retained real-byte conformance, generated Spec projection, progressive reader journey, exact site projection, and upstream KFX Site Bundle staged
- Date: 2026-07-25
- Category: portable format / authority / compatibility

## Context

Kungfu already has real, separately versioned authorities for Fact objects and
roots, Episode manifest records, journal pages and frames, import and export
catalog records, workspace layout, payload schemas, package manifests, content
digests, and the generated Spec Bundle envelope. The retained Spec 0.1 prose
predates several of these authorities and is not a safe common denominator.

Calling all of those surfaces “the format” without a composition decision
creates two opposite risks. A reader may treat one package version or
`spec_version` as if it versioned every byte and meaning. Or a replacement may
invent one mega-schema that duplicates component authorities and inevitably
drifts from the runtime.

The ambiguity is already visible in overloaded terms such as manifest, schema,
version, layout, and root. Episode Manifest, transfer manifest, Spec Bundle
Manifest, and KFX package JSON Schema are different objects with different
owners. Hana POD layout and BFBS artifacts are different schema regimes. A
journal epoch, record `schema_version`, root protocol, workspace layout version,
portable spec version, and npm package version do not advance together.

## Decision

### 1. Portable authority is composition, not consolidation

The portable-format boundary is the versioned composition of independently
owned semantic objects, containers, records, schemas, manifests, and
content-root protocols. The machine authority is
[`kungfu-portable-format-authority.contract.json`](../../framework/spec/format/kungfu-portable-format-authority.contract.json).
It references each component by stable protocol id, source role, identity
domain, version axis, and compatibility owner.

The composition contract does not copy component schemas and does not mint one
global format number. A component remains authoritative for its own semantics
and encoding. The composition states how a reader finds and orders those
authorities and which owner must decide compatibility.

### 2. Authority order is explicit

When surfaces disagree, admitted semantic objects and decisions precede named
container, record, and root protocols. Schema-owned payload interpretation
precedes package or transfer envelopes. Human documents, queries, generated
Spec Bundles, and the site are projections over those authorities.

Paths, package coordinates, URLs, process state, caches, and rendered JSON do
not replace semantic or content identity unless a named protocol explicitly
includes them in its preimage.

### 3. Identity and version domains remain distinct

Fact logical ids, immutable version roots, Cut roots, Episode ids and sealed
roots, journal page identity, payload content hashes, schema roots, transfer
inventories, package keys, and bundle inventories are not interchangeable.
Import preserves an identity only under the owning protocol's explicit rule.
Semantic migration creates a successor identity or an explicit mapping receipt.

Journal epoch, workspace layout version, POD record `schema_version`, payload
schema version, root protocol version, Spec Bundle `manifest_version`, portable
`spec_version`, and package version remain independent axes. Compatibility is
evaluated per authority and then composed against an explicit reader profile.
“Latest” is never a compatibility algorithm.

### 4. Manifest and schema terminology is closed

- **Episode Manifest** means typed append-only POD records in the Episode
  manifest journal. JSON is its folded edge projection.
- **Import/export manifest** means journal-admitted transfer inventory and
  receipts; its JSON envelope is an edge encoding.
- **Spec Bundle Manifest** means the generated `@kungfu-tech/spec` pickup and
  routing inventory. It does not own runtime semantics.
- **Package JSON Schema** means the KFX first-party artifact inventory.
- **Payload schema** has exactly one Hana POD or FlatBuffers schema owner.
- **POD layout** is a compiled closed-set record layout guarded by record
  version and fingerprints.
- **BFBS** is an exact FlatBuffers reflection artifact. Its byte digest does not
  automatically become a logical semantic root.

### 5. Compatibility ownership and replacement fail closed

Unknown well-formed material is preserved until an explicit reader, migration,
or refusal rule owns it. A projection may route, render, and package the
authority graph but cannot redefine protocol identity, compatibility, or
failure semantics.

This decision may be replaced only by a successor accepted ADR that assigns an
owner to every replaced protocol, supplies executable required-reader and
migration behavior, retains cross-version vectors for accepted and refused
paths, and regenerates Spec and site projections from the successor contract.

## Falsification and qualification

The decision is false if two listed authorities can silently claim the same
identity domain, if a package or site version changes runtime compatibility, if
an unlisted schema interprets admitted payload bytes, or if generated prose can
override a component protocol.

The staged gate verifies every referenced source and identity marker, unique
source roles, the closed terminology, independent version axes, the accepted
ADR, and the projection boundary. The required-reader contract now defines
machine-readable profiles, capability and outcome lattices, stable refusal
codes, preservation behavior for unknown records, and runtime and generated
Spec bindings. Unknown well-formed records can be inspected or preserved only
through degraded or preserve-only outcomes; they cannot be silently folded,
admitted, or executed. The migration protocol compares the full compatibility
tuple, exposes only declared directed cold-path edges, produces receipt-bound
successor identities, refuses downgrade before writes, reconciles exact retries,
and separates evidence-preserving structural repair from semantic migration.

The retained corpus preserves the v1 journal and Fact-root bytes and appends a
v2 compatibility-tuple release. Its 16 exact vectors cover all eight declared
axes and all five required-reader outcomes, and require Node and standalone
Python reader agreement. The immutable v4 alpha baseline binds the released
authority bytes and rejects incompatible mutation without an explicit
successor. The disposable migration and repair campaign verifies preview,
refusal, interruption recovery, source preservation, idempotent retry, and
receipt-bound successors without touching a user workspace. The generated
`@kungfu-tech/spec` bundle now projects the accepted authorities into eight
deterministic artifacts. Every artifact binds its exact owner source roots,
byte root, length, schema, protocol, and status; one canonical preimage
produces the bundle's normative root.
Full JSON Schema validation, committed-generation drift, installed-package
inspection, and layer qualification gates enforce that projection. The
downstream `@kungfu-tech/site` package now copies the verified Spec distribution
byte-for-byte, binds the exact manifest and normative roots, exposes stable
package-local routes for the authority overview, reader contract, version
matrix, registry, and retained vectors, and renders 11 rooted page models
without a monorepo checkout. It fails closed if the upstream status is promoted
without a deliberate contract update. The Spec package also publishes a rooted
five-level reader journey: orientation, first success, task guides, conformance
evidence, and complete reference. Its seven guides cover the Node API, JSON CLI,
independent Python reader, and retained corpus without flattening their bodies
onto the Site format landing page. Site copies those guide bytes exactly and
exposes integrity-bound render models in declared order. This reader journey is
a non-normative navigation projection; it cannot change the normative format
root or replace any component authority. This completes the site projection but
does not make the standalone format stable, publish the alpha packages, or
deploy a site.

The Site package now also emits a deterministic
`kungfu.kfx-site-bundle/v1` handoff for the independently deployed KFX
developer surface. Its source contract selects 17 versioned Site, Spec,
Buildchain, KFD, Core, and KFX inputs and maps them into 11 named facets without
copying runtime authority into the web application. The generated bundle binds
the exact source and content roots, declares canonical reader routes, and fails
closed on missing inputs, duplicate facets, undeclared source drift, or mutated
content. This upstream bundle is a portable build input for the public site; it
does not make that deployment or its navigation an authority over Kungfu
contracts.

The source acceptance gate now also closes the change-impact loop for that
handoff. An exact changed-file mapping projects KFX-owned paths onto the same 11
facets and requires either a semantic update to the KFX Site Bundle declaration
or a content-addressed no-public-content-change proof bound to the exact base,
current roots, changed paths, and affected facets. Public contracts, schemas,
SDKs, native headers, CLIs, Agent surfaces, authoring contracts, qualification
surfaces, references, and extension manifests are never proof-eligible;
unmapped owned paths and same-change weakening of the impact contract fail
closed. Negative fixtures cover missing updates, stale or forged proofs,
unmapped paths, public-surface exemption attempts, deletion and rename inputs,
and contract weakening. This gate governs synchronization only; it does not
make the Site Bundle authoritative over KFX runtime semantics.

The protected layer-artifact publisher also exposes a focused
`portable-format-alpha` scope. That scope binds one successful Actions run to
its exact source SHA, rebuilds and qualifies only `@kungfu-tech/spec` and
`@kungfu-tech/site`, refuses occupied target versions, publishes through the
existing GitHub OIDC environment without a long-lived npm token, and then
compares the public registry bytes before exercising API, CLI, standalone
Python, and all 11 site page models in a clean consumer. Cargo, PyPI, GitHub
Release assets, other npm packages, `latest`, stable compatibility, and
downstream site deployment remain outside that scope.

## Consequences

- Humans and agents receive one authority map without creating a second source
  of semantic truth.
- Component owners can evolve independently, but compatibility changes must be
  represented on their own version axis and composed explicitly.
- Required-reader profiles can be precise about what they must understand,
  preserve, refuse, migrate, or repair.
- The historical Spec 0.1 bundle remains useful input, but not normative
  implementation guidance.
- More identifiers remain visible than a single format version would expose;
  that complexity is real and is now bounded rather than hidden.

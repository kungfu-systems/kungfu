# KF-ADR-019f86da-4f90-7b3f-9ef3-84f5a878f302: KFD-2 assessments are claim-triggered jobs coordinated by the workspace coordinator

- Status: accepted; initial runtime implemented
- Date: 2026-07-11
- Category: architecture — trust-assessment lifecycle and execution topology
- Subsystem: workspace coordinator, KFD-2, Episode, query service, yijinjing
  locations/channels, embedded libkungfu, GUI/TUI, and KFX assessors
- Related: KF-ADR-019f86da-4f90-791c-9b90-4888cca36327 defines Episode; KF-ADR-019f86da-4f90-730a-a068-06e8758324e1 defines the per-data-root
  workspace coordinator; KF-ADR-019f86da-4f90-73f2-a0ac-42f14e0278d9 defines sealed Episode roots; KF-ADR-019f86da-4f90-7e38-b72f-ef8829e14104 defines
  proof-carrying queries; KF-ADR-019f86da-4f90-7d81-90a0-d144fc27fe03 binds KFD contract worlds to fact admission
  and trust assessment.

## Context

KF-ADR-019f86da-4f90-7d81-90a0-d144fc27fe03 establishes that a KFD-2 `TrustReport` assesses a concrete claim for
an intended purpose over pinned declarations, facts, and proof. It does not yet
decide when an assessment runs, which runtime component owns it, or how Desktop
and embedded products share the capability.

Running a full assessment after every agent event would burden the append path,
repeatedly evaluate irrelevant facts, and couple Episode sealing to arbitrary
domain logic. Letting each agent or GUI produce its own report would instead
create competing trust states that disappear with the process that computed
them.

Kungfu already has the required substrate: per-data-root workspace coordinators,
locations and channels, single-writer mmap journals, sealed Episodes, explicit
query cuts, and supervised multi-process execution. The assessment design
should use those primitives without making the coordinator or libkungfu a monolith.

## Decision

KFD-2 assessment is a durable, claim-triggered job:

```text
claim + purpose + pinned cut + assessment policy
  -> AssessmentRequested
  -> assessor execution
  -> Assessment Episode
  -> TrustReport
```

The recording hot path does not run a complete KFD-2 assessment. It records the
minimum facts and references that later proof cannot reconstruct reliably.
Fact admission and incremental folds may proceed independently. A report is
generated or refreshed only when a material trigger requires one.

### 1. The assessment unit is a claim for a purpose

An assessment key is derived from at least:

```text
claim identity
+ intended purpose
+ query/Episode cut or sealed root
+ contract-world and fact-surface declaration roots
+ assessment policy version
```

Examples of claims include `tests-passed`, `task-completed`, and
`release-ready`. Purposes distinguish whether the same evidence is sufficient
for progress display, handoff, customer communication, or production release.

Agent self-reporting may create a claim and trigger assessment. It is evidence
about what the agent asserted, not sufficient authority to prove its own claim.

### 2. Assessments run at material boundaries, not per append

The standard triggers are:

- a load-bearing claim is recorded;
- a declared milestone, checkpoint, handoff, or Episode seal occurs;
- a user or agent requests a trust decision;
- a high-risk action requires a fresh report;
- admitted evidence, declarations, or assessment policy materially change.

Ordinary commands, logs, and unrelated facts do not cause full reevaluation.
Reports carry explicit lifecycle state such as `pending`, `running`, `fresh`,
`stale`, `insufficient-evidence`, `conflicted`, `unverifiable`, and
`failed-retryable`.

An open Episode may support a provisional report at an explicit frontier. A
sealed cut supports a stable, reproducible report. New facts do not mutate an
older report; they may make it stale and produce a successor.

### 3. Episode seal persists intent; assessment is asynchronous by default

The normal seal path synchronously:

1. accepts the final facts and admission outcomes;
2. closes the Episode and commits its sealed content root;
3. durably records or makes deterministically discoverable any required
   `AssessmentRequested` jobs;
4. returns a seal receipt whose trust state may be `pending`.

It does not execute an unbounded assessment in the recorder's call stack.
Assessment failure cannot roll back or invalidate a successfully sealed
Episode.

High-risk decisions may explicitly await or require a report. A timeout means
the Episode remains sealed while the guarded action fails closed because trust
is pending or insufficient.

### 4. Desktop workspace coordinator coordinates assessment jobs

For a live Desktop data root, the workspace coordinator owns:

- trigger discovery and durable job scheduling;
- assessment-key deduplication;
- dependency tracking and precise report invalidation;
- executor selection, timeout, cancellation, retry, and health;
- acceptance and publication of assessment results;
- subscription updates consumed by GUI, CLI, TUI, and agents.

The coordinator remains a coordinator, not fact authority and not the universal
implementation of every assessor. Durable requests, reports, Episodes, and
proof remain in the data-root ledger. The per-user supervisor only starts and
routes to the correct workspace coordinator; it does not assess workspace claims.

If no live coordinator exists, a daemonless or embedded host may schedule assessment
against closed data through the same contracts.

### 5. Process assessors use locations, channels, and single-writer journals

Desktop defaults to a managed assessor worker process for isolation and
independent lifecycle. The worker receives immutable coordinates rather than a
moving in-memory workspace:

- assessment key, claim, and purpose;
- QueryDefinition and pinned cut;
- Episode and declaration roots;
- assessment policy, deadline, and allowed capabilities.

It reads the required sealed journals through read-only mmap and writes results
through its own assessor location and single-writer journal. Multiple processes
must not concurrently write the same mmap journal file.

The assessor does not append to the already sealed work Episode. It produces a
separate Assessment Episode that causally depends on the assessed Episode,
declarations, and query proof. The workspace coordinator validates and admits that
result into the workspace fold.

Durable request plus idempotent assessment key makes crash recovery at-least
once but logically single-result: the coordinator can retry an interrupted worker
without inventing a second assessment identity.

### 6. Embedded products use the same contract with thread execution

Execution placement is replaceable:

```text
InlineExecutor   -> tests and bounded synchronous checks
ThreadExecutor   -> trusted embedded/default libkungfu assessment
ProcessExecutor  -> Desktop default
SandboxExecutor  -> untrusted or high-risk third-party assessor
```

All executors consume the same `AssessmentRequest` and produce the same
`AssessmentResult`. Equivalent pinned inputs and policy must produce equivalent
report hashes regardless of executor profile.

Moving from process to thread does not weaken semantic isolation. In-process
assessors retain explicit location identity, pinned-cut reads, single-writer
report commit, cancellation/timeout state, and Assessment Episode output.
Thread-local context may accelerate location binding, but persisted identity
must never depend only on implicit thread state.

Trusted deterministic assessors may run in a thread. Untrusted native code,
unsafe third-party libraries, or assessors needing stronger fault containment
remain process/sandbox candidates because a thread crash can terminate the
embedded host.

### 7. GUI uses progressive disclosure

The normal human path is:

```text
current state and progress
  -> TrustReport and fitness for purpose
  -> proof and evidence
  -> Episode timeline/replay
  -> raw observations and diagnostics
```

Users are not required to inspect replay for routine status checks. The GUI
shows report freshness, purpose, missing evidence, conflict, and residual risk.
Replay is a drill-down for investigation and reproduction, not the default
dashboard tax. GUI state does not own assessment meaning.

## Implementation sequence

1. Define typed assessment request/key/result and report lifecycle states. Make
   seal persist or deterministically expose assessment intent without waiting.
2. Add one built-in deterministic assessor over a sealed Episode and
   proof-carrying query; store its result as a dependent Assessment Episode.
3. Add workspace-coordinator scheduling, deduplication, retry, precise invalidation,
   and subscription updates with one process executor.
4. Add the equivalent libkungfu thread executor and conformance fixtures
   comparing report hashes across process and thread execution.
5. Add explicit `await`/`require trust` decision gates and a GUI progression
   from summary to report, proof, and replay.

The initial vertical slice is implemented in `libkungfu` and the workspace
coordinator. `assessment_event.fbs` owns request, execution, result, invalidation,
and report persistence. The request coordinator journal is separate from the
per-key/per-executor assessor journals, so managed process and embedded thread
executors retain distinct locations and single-writer result paths. The Python
workspace coordinator schedules one pending process worker at a time and publishes a
subscription fold to `coordinator/assessments.json`; CLI and GUI surfaces show
freshness and fitness before proof/replay details. Native C ABI, Node, Python,
process, and thread fixtures cover the shared contract. The embedded `thread`
profile dispatches the C++ assessment body through a dedicated joined thread;
its persisted execution record proves separate-thread placement while report
identity remains derived only from pinned semantic inputs.

## Acceptance gates

- Append throughput and Episode seal do not depend on completing an unbounded
  KFD-2 assessment.
- A sealed Episode plus durable request survives recorder/coordinator/worker restart
  and eventually produces one logical report or an explicit terminal state.
- Reports bind claim, purpose, pinned cut, declarations, evidence, policy, and
  residual risk; no moving-head evaluation is described as reproducible.
- Irrelevant new facts do not invalidate unrelated reports; relevant
  correction, retraction, or declaration change does.
- Assessor workers use distinct location identity and single-writer journals;
  no concurrent multi-writer mmap path is introduced.
- Assessment output is a separate dependent Episode and never mutates a sealed
  work Episode.
- Process and thread executors produce equivalent report hashes for shared
  fixtures.
- A high-risk gate fails closed on missing, stale, timed-out, or insufficient
  trust without reporting Episode seal failure.
- A user can understand routine status and fitness for purpose before opening
  proof or replay.

## Consequences

- KFD-2 becomes a natural use of Kungfu's existing runtime substrate rather
  than a synchronous validation tax on recording.
- Desktop keeps durable assessment work alive after an agent or GUI exits.
- Embedded consumers retain full local trust capability without requiring the
  Desktop process topology or managed-language runtimes.
- The coordinator gains scheduler responsibilities but not domain-specific assessor
  logic or fact authority.
- Assessment reports become replayable, queryable facts with explicit
  freshness instead of ephemeral dashboard judgments.

## Alternatives considered

- **Assess every append synchronously.** Rejected because most events are not
  load-bearing claims and arbitrary evaluator cost would enter the hot path.
- **Run the full assessment inside `episode.seal()`.** Rejected because a slow
  or failed assessor must not prevent durable Episode closure.
- **Let each agent or GUI assess independently.** Rejected because trust state
  would fork and disappear with process lifecycle.
- **Let workers write the coordinator's journal directly.** Rejected because it
  violates single-writer journal semantics.
- **Append the report to the sealed work Episode.** Rejected because sealing is
  immutable; assessment is a dependent causal object.
- **Create separate Desktop and embedded trust models.** Rejected because
  process/thread placement is an execution choice, not a semantic fork.

## Residual risk

- Existing runtime components may contain process-global or thread-affine
  assumptions; a bounded executor spike must test location and writer lifetime
  before calling the thread implementation trivial.
- Assessment dependency graphs can grow large. Precise invalidation should
  start with one real claim family rather than a general rule engine.
- Domain assessors can be nondeterministic or unsafe. Reports must disclose
  determinism and executor/policy versions, and untrusted implementations need
  stronger isolation.

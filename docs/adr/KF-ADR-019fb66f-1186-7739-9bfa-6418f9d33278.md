# KF-ADR-019fb66f-1186-7739-9bfa-6418f9d33278: Node watcher lifecycle work runs outside the libuv worker pool

- Status: accepted; implementation staged for protected qualification
- Date: 2026-07-31
- Subsystem: Node binding watcher lifecycle, journal consumption, and
  snapshot handoff
- Preserves: yijinjing journal and RxCpp routing, current-state snapshot
  semantics, explicit `sync()` compatibility, typed runtime errors, replay,
  and System KFX ownership of product snapshot meaning

## Context

The historical
[Node watcher snapshot proposal](KF-ADR-019f86da-4f90-7fb3-a803-393d3bbe6704.md)
was withdrawn because its declared state-size and UI-fidelity trigger had not
materialized. It correctly required a future decision to bring retained
thread-pool occupancy, state-size, lock-hold, and fidelity evidence instead of
treating the old option list as permanent backlog. The related
[control/event-axis assessment](KF-ADR-019f86da-4f90-7f7b-90be-c002b024d412.md)
continues to freeze the RxCpp routing algebra; this decision does not reopen
that event-axis choice.

The operational trigger is now measured independently of state size. Before
this change, one live watcher submitted its lifetime loop through
`uv_queue_work`. With `UV_THREADPOOL_SIZE=1`, a 1,000-iteration
`crypto.pbkdf2` submitted after `watcher.start()` did not complete within the
1.5-second deadline. The watcher therefore reserved the process's only libuv
worker slot even when journal traffic and product state were idle.

The existing snapshot shape remains desirable. Journal and RxCpp processing
fold native state continuously, while Node observes a bounded current-state
snapshot rather than one callback per journal frame. Product-specific meaning
belongs to System KFX and Domain Profiles, not to this Core binding.

## Decision

One watcher owns one dedicated native thread for its long-lived
journal/reactor step loop. It no longer reserves a libuv worker-pool job.
Journal readers, RxCpp declarations, replay behavior, and public watcher
construction remain unchanged.

The dedicated thread communicates with the Node environment through one
`Napi::ThreadSafeFunction` whose native-to-Node queue capacity is exactly one.
Snapshot requests coalesce while one delivery is pending. This queue is a
wakeup edge for a current-state fold, not a second fact stream: journal order
and custom transport frames stay on their existing ordered paths. The Node
thread performs N-API serialization under the existing feed mutex, preserving
the rule that native worker code does not touch JavaScript values.

Quit, fatal worker error, and environment cleanup request stop and join the
dedicated thread. A normal coordinator disconnect waits on that native thread
before reconnecting; it does not sleep on the Node event loop. The stopped
event is ordered after any pending snapshot event, and fatal errors retain the
existing typed JavaScript mapping.

`Watcher.runtimeStats()` exposes the versioned
`kungfu.node-watcher-runtime-stats/v1` diagnostic contract:

- step duration and worker lock-wait count, mean, and maximum;
- snapshot request, delivery, coalescing, lock-wait, and lock-hold measures;
- the fixed bridge capacity, current queue depth, and bridge failures; and
- the existing custom-frame queue frames, bytes, fixed four-MiB capacity, and
  explicit drops.

These measures diagnose pressure; they are not a real-time scheduling
guarantee and do not transfer product semantics into Core.

## Deliberate non-decisions

- No dirty-key diff, double-buffered product snapshot, or lock-free state
  handoff is introduced. The retained lock measures must show a separate
  state-size trigger before adding that complexity.
- The RxCpp routing algebra, reactor step primitive, journal layouts, and
  replay model do not change.
- Snapshot coalescing does not authorize loss or reordering of journal facts
  or custom transport frames.
- The Node binding does not interpret KFX domain state or become a product
  callback dispatcher.

## Consequences

- Long-lived watcher work consumes one explicit native thread instead of one
  process-global libuv pool slot.
- The native-to-Node backlog is structurally bounded at one wakeup, including
  when the Node consumer is slow.
- Shutdown has a join boundary that can be qualified directly during quit and
  environment cleanup.
- The design adds thread lifecycle and bridge state that must remain race-free
  across start, disconnect, error, quit, and addon cleanup.
- Existing four-MiB custom-frame overflow remains an explicit gap that callers
  must handle; it is not hidden by snapshot coalescing.

## Qualification and falsifiers

The retained
[Node watcher runtime boundary qualification](../qualification/node-watcher-runtime-boundary.md)
records the commands, measured baseline, and non-claims. Local macOS evidence
requires:

```sh
./shifu test:node-watcher-runtime-boundary
./shifu test:agent-session-peer-transport:native
./shifu core:architecture:health
```

The real native transport fixture writes a 512-frame burst, stalls the Node
consumer for 250 milliseconds, and requires the final ordered frame, observed
snapshot coalescing, real step and snapshot timing, zero bridge failure, and
zero custom-frame drop. The qualified Core candidate action reruns both
watcher suites after rebuilding on protected Darwin arm64/x64, Linux x64, and
Windows x64 candidates.

This decision is falsified if a watcher again consumes a libuv worker-pool job;
if its native-to-Node callback backlog can exceed one; if a callback touches
JavaScript after environment cleanup; if quit or cleanup can leave a joinable
thread behind; if snapshot coalescing loses ordered custom frames; if Core
acquires product snapshot meaning; or if the exact-revision protected platform
matrix fails.
